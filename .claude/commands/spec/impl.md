# ③Go実装仕様書 作成

設計3段（①Rails現行仕様書 → ②Go移行・設計仕様書 → ③Go実装仕様書）の③番目の手順です。ここで作る文書が、実装フロー（`/impl:plan` 以降）の入力になります。

## 最初に必ず読むファイル

**他の作業の前に、以下を順に読み込んでください。読まずに書き始めてはいけません。**

1. `計画書/Go実装仕様書/Go実装仕様書_自動生成プロンプト.md`
2. 対象機能の②`〇〇機能_Go移行・設計仕様書.md`
3. `計画書/規約/アーキテクチャ規約.md`（とくに「3. 設計パターンごとの構造適用方針」「12. Error変換パターン（AppError）」）
4. `計画書/規約/コーディング規約.md`
5. `計画書/規約/Gorm規約.md`
6. `計画書/規約/Gin規約.md`（Presentation層・ルーティング・ミドルウェアを記載するとき）

自動生成プロンプトが、②の分析方針・パターン別の前提アーキテクチャ・文書分割ルール・出力フォーマット・禁止事項をすべて規定しています。以降の作業は、このプロンプトの指示に従ってください。本コマンドの記載とプロンプトが矛盾する場合は、プロンプトを優先します。

## 入力

`$ARGUMENTS` を解釈してください。想定される内容:

- 1つ目: 対象の機能名、または②`〇〇機能_Go移行・設計仕様書.md` のパス
- 2つ目（省略可）: 出力先ディレクトリ。省略時は `../edu-platform/rails/tmp/Go実装仕様書`

パスはいずれもこのリポジトリのルートからの相対パスです。

機能名だけ渡された場合は、`../edu-platform/rails/tmp/GO移行・設計仕様書` 配下から対応する②を探してください。複数候補があるときはユーザーに確認してください。

## 作業内容

1. プロンプト・②・規約を読み込む
2. 出力先に同名ファイルが既にある場合、上書き前にユーザーに確認する
3. プロンプト「②仕様書の分析方針」の全項目を②から抽出する。②に記載がない項目は③側で判断せず、②に立ち返る
4. ②「4. 設計パターン」の採用パターンを確認し、プロンプト「前提アーキテクチャ」の該当する構造（Domain Model / Event Sourcing、Active Record、Transaction Script）のみを反映する
5. ディレクトリ構成を確定し、**実装ファイル数を数える**（テストファイルは一覧に含めないが、分割判断はテスト込み＝実装の約1.7倍で行う）
6. 実装ファイルが20以上になる場合、プロンプト「文書の分割（1文書あたり30〜35ファイル）」に従って文書を分割する。原則は Handler ファイル単位のスライス分割。Handlerが1つしかない機能はレイヤーで割る
7. プロンプト「出力フォーマット」の各節で出力する

## 出力

分割しない場合:

```
〇〇機能_Go実装仕様書.md
```

分割する場合（1文書＝1PRに保つため）:

```
〇〇機能_Go実装仕様書_1_基盤.md
〇〇機能_Go実装仕様書_2_<スライス名>.md
〇〇機能_Go実装仕様書_3_<スライス名>.md
```

スライス名は、担当するエンドポイント群が分かる日本語にしてください（例: `セッション`・`パスワードリセット`）。レイヤーで割った場合は `_1_Domain` ・`_2_Infrastructure`・`_3_Application・Presentation` のようにします。分割した場合、共通の実装方針はスライス編で繰り返さず基盤編を参照させ、基盤編のディレクトリ構成に「どの文書がどのファイルを担当するか」の対応表を載せてください。

## 禁止事項

- 自動生成プロンプトを読まずに書き始める
- ②で決定した内容（Bounded Context・設計パターン・Aggregate・Entity・Value Object・Repository・UseCase・Transaction境界・Validation方針・Authorization方針・Error設計・Domain Event・API互換方針・DB方針・テスト戦略）を変更する。②に矛盾する実装案を出す
- `計画書/規約/` に反する実装方針を書く。規約に定めのない事項について独自ルールを新設する
- Domain Model 前提のフルレイヤー構成を、Transaction Script / Active Record 採用機能に一律で適用する
- 完全に動作するアプリケーションコード（関数本体のロジック）を書く
- ②に記載のない実装詳細を、「②からの補足」と明示せずに書く
- 1文書が30〜35ファイルを超えたまま分割せずに出力する
- 変更履歴を示す表現（「追記」「更新」「差分」「新規追加」等）を文書に書く

## 既存の③を直す場合

必要な範囲にとどめ、ピンポイントで修正してください。文書全体を書き直さないこと。

## 完了時

以下を提示してください。

- 採用した設計パターンと、それに応じたディレクトリ構成
- 実装ファイル数とテスト込みの見積り、分割したかどうかとその単位
- 「②からの補足」として書いた箇所の一覧
- 未確定事項（②に記載がなく判断が必要だった箇所）

そのうえで、実装に進む場合は `/impl:plan` に、この③のパスを渡す旨を伝えてください。
