# ②Go移行・設計仕様書 作成

設計3段（①Rails現行仕様書 → ②Go移行・設計仕様書 → ③Go実装仕様書）の②番目の手順です。

## 最初に必ず読むファイル

**他の作業の前に、以下を順に読み込んでください。読まずに書き始めてはいけません。**

1. `計画書/GO移行・設計仕様書/Go移行・設計仕様書_自動生成プロンプト.md`
2. 対象機能の①`〇〇機能_Rails現行仕様書.md`
3. `計画書/規約/アーキテクチャ規約.md`（とくに「2. レイヤー責務と依存方向」「3. 設計パターンごとの構造適用方針」「5. Context間連携ルール」）

自動生成プロンプトが、①の分析方針・前提アーキテクチャ・設計パターン判断基準・Domain Model採用基準・出力フォーマット（全23節）・禁止事項をすべて規定しています。以降の作業は、このプロンプトの指示に従ってください。本コマンドの記載とプロンプトが矛盾する場合は、プロンプトを優先します。

## 入力

`$ARGUMENTS` を解釈してください。想定される内容:

- 1つ目: 対象の機能名、または①`〇〇機能_Rails現行仕様書.md` のパス
- 2つ目（省略可）: 出力先ディレクトリ。省略時は `../edu-platform/rails/tmp/GO移行・設計仕様書`

パスはいずれもこのリポジトリのルートからの相対パスです。

機能名だけ渡された場合は、`../edu-platform/rails/tmp/Rails現行仕様書` 配下から対応する①を探してください。複数候補があるときはユーザーに確認してください。

## 作業内容

1. プロンプト・①・アーキテクチャ規約を読み込む
2. 出力先に同名ファイルが既にある場合、上書き前にユーザーに確認する
3. プロンプト「Rails現行仕様書の分析方針」に従って①から情報を抽出する
4. プロンプト「設計パターン判断」「Domain Model採用基準」に従い、採用パターン（Transaction Script / Active Record / Domain Model / Event Sourcing）を判断根拠つきで決める
5. 採用パターンに応じて、規約「3. 設計パターンごとの構造適用方針」の対応を踏まえて各節を書く
6. プロンプト「出力フォーマット」の全23節で出力する

## 出力

`〇〇機能_Go移行・設計仕様書.md`

## 禁止事項

- 自動生成プロンプトを読まずに書き始める
- 実装コード・サンプルコードを書く（②は設計レベル。Goの型名・SQL・GORMのクエリは③の担当）
- `計画書/規約/` に反する設計を書く。規約に定めのない事項について独自ルールを新設する
- Domain Model を前提としたフルレイヤー構成を、全機能に一律で適用する
- ①に根拠のない業務要件を新設する。根拠がない判断を断定する（「推測」と明記する）
- 変更履歴を示す表現（「追記」「更新」「差分」「新規追加」等）を文書に書く

## 既存の②を直す場合

必要な範囲にとどめ、ピンポイントで修正してください。文書全体を書き直さないこと。その機能の③にも影響が及ぶ場合は、影響箇所を挙げてユーザーに伝えてください（③の修正は自動で始めない）。

## 完了時

採用した設計パターンとその判断根拠、未確定事項を提示してください。次は `/spec:impl` で③Go実装仕様書に進む旨を伝えてください。
