# 実行計画書 作成

これは実装フロー(①実行計画書 → ②セルフチェック → ③コード生成 → ④セルフチェック → ⑤カバレッジ保管 → ⑥Quality Review)の①番目の手順です。

## 入力

`$ARGUMENTS` を解釈してください。想定される内容:

- 1つ目: 対象機能の「〇〇機能_Go実装仕様書」（③）のファイルパス
- 2つ目（省略可）: 規約ドキュメント（アーキテクチャ規約・コーディング規約・Gorm規約・Gin規約等）が置かれているディレクトリパス。省略時は③と同じプロジェクト内の`規約/`ディレクトリ、または近傍を探索する

パスが曖昧・不足している場合は、カレントディレクトリ以下を検索して該当しそうなファイルを探し、複数候補がある場合はユーザーに確認してください。

## 目的

③実装仕様書に書かれた内容を、**実際に着手できる作業手順**に分解した「〇〇機能_実行計画書.md」を作成してください。この計画書自体はコードを書かず、次工程（③コード生成を担当するサブエージェント）がそのまま作業計画として使える粒度にしてください。

## 作業内容

1. ③実装仕様書と規約ドキュメントを読み込む
2. ③「1. 機能概要」から、対象Bounded Context・採用設計パターン（Transaction Script / Active Record / Domain Model / Event Sourcing）を確認する
3. ③「2. ディレクトリ構成」に記載された作成対象ファイルを列挙し、依存関係（例: domain → application → infrastructure → presentation、テストは対応する実装の直後）を考慮した作成順序を決める
4. ファイルごとに、実装すべき要点を③該当セクションから抽出して要約する（関数本体のロジックはまだ書かない。あくまで「何を実装するか」の一覧）
5. ③「16. テストケース設計」に記載の全テストケースを一覧化し、どのテストファイルに対応するか紐付ける
6. ③に明記がなく、実装のために追加の判断が必要な箇所があれば「未確定事項」として列挙し、暫定的な方針案があれば「推測」と明記する
7. 後続の③コード生成ステップでは、この機能を1機能=1サブエージェントに担当させ、該当する全レイヤーとテストコードを一括実装させる方針であることを明記する

## 出力ファイル

`〇〇機能_実行計画書.md`（③実装仕様書と同じディレクトリに保存。既に同名ファイルがある場合は上書き前に確認する）

## 出力フォーマット

```markdown
# 〇〇機能 実行計画書

## 1. 概要
- 対象Bounded Context
- 採用設計パターンと理由（③からの要約）
- 実装先プロジェクトの想定（不明な場合はユーザーに確認）

## 2. 作成ファイル一覧・順序
| 順序 | ファイルパス | 種別（実装/テスト） | 依存関係 |
|-|-|-|-|

## 3. ファイルごとの実装要点
### {ファイルパス}
- 実装すべき内容（③の該当セクション番号を明記して要約）

## 4. テストケース一覧
| 対応ファイル | テスト区分 | テストケース |
|-|-|-|

## 5. 未確定事項
| 項目 | 現状の方針案 | 推測かどうか | ③のどこにも記載がない旨 |
|-|-|-|-|
（なければ「なし」と記載）

## 6. 次工程（③コード生成）への申し送り
- サブエージェント方針: 1機能=1サブエージェント、対象レイヤー・テストコードを一括実装
- 実装先プロジェクトのパス（②セルフチェック・③コード生成で使用）
```

## 禁止事項

- ③・規約に反する計画を立てる
- 完全な実装コードをこの計画書内に書く（あくまで計画であり、コード生成は次工程）
- ③に記載のない業務要件を新設する

## 完了時

計画書を作成したら、次は `/impl:plan-check` でAIセルフチェック＋目視確認に進む旨をユーザーに伝えてください。
