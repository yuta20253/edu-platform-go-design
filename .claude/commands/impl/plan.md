# 実行計画書 作成

これは実装フロー(①設計整合チェック → ②実行計画書 → ③セルフチェック → ④コード生成 → ⑤セルフチェック → ⑥カバレッジ保管 → ⑦Quality Review)の②番目の手順です。①設計整合チェックで「OK」の判定が出ていることを前提とします。

## 入力

`$ARGUMENTS` を解釈してください。想定される内容:

- 1つ目: 対象機能の「〇〇機能_Go実装仕様書」（③）のファイルパス
- 2つ目（省略可）: 規約ドキュメント（アーキテクチャ規約・コーディング規約・Gorm規約・Gin規約等）が置かれているディレクトリパス。省略時は③と同じプロジェクト内の`規約/`ディレクトリ、または近傍を探索する

パスが曖昧・不足している場合は、カレントディレクトリ以下を検索して該当しそうなファイルを探し、複数候補がある場合はユーザーに確認してください。

## 目的

③実装仕様書に書かれた内容を、**実際に着手できる作業手順**に分解した「〇〇機能_実行計画書.md」を作成してください。この計画書自体はコードを書かず、次工程（④コード生成を担当するサブエージェント）がそのまま作業計画として使える粒度にしてください。

**実装はテスト駆動開発（TDD）で行う。** 実装ファイル1つにつき、対応するテストファイルを先に書き、実行して失敗することを確認した上で（Red）、実装ファイルを書いて成功させる（Green）、という順序を本計画書に反映してください。ファイル単位のペアをTDDサイクルの最小単位とします。

## 作業内容

1. ③実装仕様書と規約ドキュメントを読み込む
1-2. 実装先リポジトリ(通常は`../edu-platform`)で、作業ブランチを用意する。
   - 現在のブランチと未コミットの変更を確認する(`git -C <実装先> branch --show-current`・`git -C <実装先> status`)。他の作業中ブランチ・未コミットの変更がある場合は、それに触れずユーザーに確認する
   - `main`から作業ブランチを作成する。ブランチ名はユーザーに確認する。新規リポジトリの作成(`git init`)は行わない
   - 作成したブランチ名を、実行計画書「1. 概要」に記載する。④コード生成はこのブランチ上で行う
2. ③「1. 機能概要」から、対象Bounded Context・採用設計パターン（Transaction Script / Active Record / Domain Model / Event Sourcing）を確認する
3. ③「2. ディレクトリ構成」に記載された作成対象ファイルを列挙し、実装ファイルと、それに対応するテストファイル（同名の`_test.go`等）を1対1で対応付ける。1つの実装ファイルに複数のテストケースがある場合も、対応するテストファイルは1つである
4. レイヤー間の依存関係（domain → application → infrastructure → presentation）に従って着手するレイヤーの順序を決める。**各ファイルペアは、必ずテストファイルを実装ファイルより先に置く順序とする**（TDD。Red→Greenの順）
5. ③「16. テストケース設計」（または該当節）に記載のテストケースを、対応する実装ファイルのペアに紐付ける。UseCase Test・Store Test・Repository Test等、1つの実装ファイルに対応する単体テストはペアとして扱う。Integration Test等、複数ファイルをまとめて検証するテストはファイルペアの対象外とし、「5. 統合テスト一覧」として全ペア完了後に実施する扱いにする
6. ファイルごとに、実装すべき要点を③該当セクションから抽出して要約する（関数本体のロジックはまだ書かない。あくまで「何を実装するか」の一覧）
7. ③に明記がなく、実装のために追加の判断が必要な箇所があれば「未確定事項」として列挙し、暫定的な方針案があれば「推測」と明記する
8. 後続の④コード生成ステップでは、この機能を1機能=1サブエージェントに担当させる。進め方は「2. TDDステップ一覧」の順に、1ステップ=1ファイルペアとして、テストファイルを書いて失敗を確認し（Red）、対応する実装ファイルを書いて成功を確認する（Green）サイクルを繰り返す方針であることを明記する

## 出力ファイル

`〇〇機能_実行計画書.md`（③実装仕様書と同じディレクトリに保存。既に同名ファイルがある場合は上書き前に確認する）

## 出力フォーマット

```markdown
# 〇〇機能 実行計画書

## 1. 概要
- 対象Bounded Context
- 採用設計パターンと理由（③からの要約）
- 実装先プロジェクトの想定（不明な場合はユーザーに確認）
- 実装先の作業ブランチ名（作業内容1-2で作成したもの）

## 2. TDDステップ一覧（テスト→実装のペア順）
| 順序 | テストファイル | 対応する実装ファイル | このステップで書くテストケース（③「16. テストケース設計」等の該当箇所） | 依存関係 |
|-|-|-|-|-|

各ステップは「①テストファイルを書く → ②実行して失敗を確認する（Red） → ③対応する実装ファイルを書く → ④実行して成功を確認する（Green）」の単位である。レイヤー間の依存（domain → application → infrastructure → presentation）に従い、依存される側のペアを先に完了させる。

## 3. ファイルごとの実装要点
### {ファイルパス}
- 実装すべき内容（③の該当セクション番号を明記して要約）

## 4. 未確定事項
| 項目 | 現状の方針案 | 推測かどうか | ③のどこにも記載がない旨 |
|-|-|-|-|
（なければ「なし」と記載）

## 5. 統合テスト一覧（全ペア完了後に実施）
| テストケース | 対応するテストファイル | 検証内容 |
|-|-|-|
（③「16. テストケース設計」のIntegration Test等。ファイルペア単位に紐付けられないテストが対象。なければ「なし」と記載）

## 6. 次工程（④コード生成）への申し送り
- 進め方: 「2. TDDステップ一覧」の順に、1ステップ=1ファイルペアとして、テスト作成・Red確認 → 実装作成・Green確認、を繰り返す。全ステップ完了後に「5. 統合テスト一覧」を実施する
- サブエージェント方針: 1機能=1サブエージェント。対象レイヤー全体を担当するが、**実装の進め方はレイヤー一括ではなくTDD（Red→Green）のサイクルをファイルペア単位で繰り返す**
- 実装先プロジェクトのパス（③セルフチェック・④コード生成で使用）
```

## 禁止事項

- ③・規約に反する計画を立てる
- 完全な実装コードをこの計画書内に書く（あくまで計画であり、コード生成は次工程）
- ③に記載のない業務要件を新設する
- 実装ファイルをテストファイルより先に並べる（TDDの順序に反する）

## 完了時

計画書を作成したら、次は `/impl:plan-check` でAIセルフチェック＋目視確認に進む旨をユーザーに伝えてください。
