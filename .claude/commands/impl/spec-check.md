# 設計整合チェック（実装着手前）

これは実装フロー(①設計整合チェック → ②実行計画書 → ③セルフチェック → ④コード生成 → ⑤セルフチェック → ⑥カバレッジ保管 → ⑦Quality Review)の①番目の手順です。

## なぜこの工程があるか

③実装仕様書は①②を経て作られますが、次の種類のずれは③だけを読んでいても見つかりません。実装に着手してから気づくと、コードと3つの文書を同時に直すことになります。**実装前にここで潰します。**

- 文書間の参照が、実在しない節を指している（他機能の文書への参照を含む）
- ②③が、自機能の①に無い事実を出所なしに断定している
- ①②③が互いに矛盾している（とくに③のテストケースの期待値が①②と逆）
- ①が実装の根拠を欠いている（カラムの型・NULL可否・一意制約など）
- Railsの実体と乖離している（レスポンスのラップ・フィールド・型、`enum`の保持形式、N+1）
- 規約の章番号・章名が古い、または規約に反している
- 同一Bounded Contextを共有する他機能の③と、型・メソッドシグネチャがずれている

## 入力

`$ARGUMENTS` を解釈してください。想定される内容:

- 1つ目: 対象機能の「〇〇機能_Go実装仕様書」（③）のパス
- 2つ目（省略可）: 規約ディレクトリのパス。省略時は`計画書/規約/`
- 3つ目（省略可）: Railsリポジトリのパス。省略時は`../edu-platform`

③のパスから機能名を取り、同じ機能の①②を探してください。あわせて、③「2. ディレクトリ構成」の対象Bounded Context名で、**同じContextを宣言している他機能の②③**も特定してください（Model・Storeを共有している可能性があります）。

## 作業内容

### 1. 参照の解決確認

①②③が `〜「N. 節名」` の形で参照しているすべての箇所を抽出し、参照先の文書にその見出しが**実在するか**を1件ずつ照合してください。規約への参照（`規約「N. ...」`）も現行の規約の見出しと照合します。

件数が多くなるため、目視ではなく grep 等で**全件を列挙してから**照合してください。参照先が他機能の文書でまだ作成されていない場合は、「未作成（マージ順の制約）」として区別します。

### 2. 根拠の追跡

②③が断定しているRailsの挙動・データ構造について、根拠が次のいずれかであることを確認してください。

- 自機能の①にある
- 他機能の①にあり、**どの文書のどの節か**が明記されている
- 「推測」「②からの補足」と明記されている

いずれでもないものは「出所なしの断定」として挙げます。

### 3. ①②③の相互矛盾

- ③「テストケース設計」の期待値が、①の業務ルール・②の設計と逆になっていないか
- ②が「変更しない」と書いた項目を、③が実際に変えていないか
- ②の責務分担（どのContext・どの層が何をするか）と、③の処理順序が一致しているか
- ③が本文で定義している型・ファイルが「2. ディレクトリ構成」のファイル一覧に含まれているか。本文で参照しているのに定義がない型はないか

### 4. Rails実体との突き合わせ

Railsリポジトリは**読み取りのみ**です。参照前に `git -C <Railsパス> branch --show-current` で `main` であることを確認してください。`main` でない場合は**ブランチを切り替えず**、`git -C <Railsパス> show main:<ファイルパス>` で main の内容だけを読みます。

- **Controller**: レスポンスの最上位のラップ（`{"teacher": {...}}` 等）・ステータスコード・エラー時のボディ形式
- **Serializer**: 返すフィールドの集合（③が余計なフィールドを足していないか、足りないか）とネストの形
- **Model**: `enum` の保持形式（整数か文字列か）・検証・スコープ
- **schema**: カラムの型・NULL可否・一意インデックス
- **一覧取得**: Railsが `includes` / `preload` で一括取得している箇所を、③がループで個別取得していないか（N+1）

### 5. 規約との整合

規約（アーキテクチャ・コーディング・Gorm・Gin）と③を突き合わせます。とくにディレクトリ構成・Transaction・Error変換・認可とCSRFの適用範囲・レスポンス形式を確認してください。

規約に定めのない事項を③が独自に決めている場合は挙げてください。規約に書くべき内容だと判断した場合は、③を直す前にユーザーに確認します。規約どうしが矛盾している場合も指摘対象です（この場合の修正先は規約です）。

### 6. 共有Contextの他機能③との整合

同じBounded Contextを共有する他機能の③がある場合、共有するstruct・Store・インターフェースの**フィールドとメソッドシグネチャが一致しているか**を照合してください。片方の③にしかないフィールドを他方が必要としていないか（例: 一方の視点だけが返す項目の元になるフィールド）も確認します。

## 出力ファイル

`〇〇機能_設計整合チェック結果.md`（③実装仕様書と同じディレクトリ）

## 完了時

**ここで停止してください。** 指摘事項を自動で①②③に反映しないこと。①②③は設計の正本であり、直すときは対応する自動生成プロンプトと規約を読み直す必要があります（`CLAUDE.md`）。

- **「要修正」が1件でもある場合**: `/impl:plan` には進まないこと。指摘事項と修正先を提示し、どれを直すかユーザーに確認してください。修正後は再度このコマンドを実行します
- **すべてOKの場合**: 次は `/impl:plan`（②実行計画書）に進む旨を伝えてください

## 禁止事項

- 指摘事項をユーザーの承認なしに①②③へ反映する
- Railsリポジトリのファイルを変更する・ブランチを切り替える・コミットする
- 参照の照合を目視で済ませ、全件を列挙しない
- 「要修正」のまま `/impl:plan` に進む
- 指摘事項を実際より甘く（または厳しく）評価する
