# ソースコード・テストコード生成（サブエージェント委譲）

これは実装フローの③番目の手順です。②で承認済みの実行計画書をもとに、実際のソースコードとテストコードを実装します。

**運用ルール: この工程のコーディング作業は、メインエージェント（このセッション）が直接書かず、必ずAgentツール（サブエージェント）に委譲してください。** これは今後のソースコード作成全般に適用される恒久的な方針です。

## 入力

`$ARGUMENTS` を解釈してください。想定される内容:

- 1つ目: ②で承認済みの「〇〇機能_実行計画書.md」のパス
- 2つ目: 「〇〇機能_Go実装仕様書」（③）のパス
- 3つ目: 規約ドキュメント（アーキテクチャ規約・コーディング規約・Gorm規約・Gin規約）が置かれているディレクトリのパス
- 4つ目: 実装先プロジェクト（実際にコードを配置するGo/Railsリポジトリ）のルートパス

いずれかが不明な場合、進める前にユーザーに確認してください（実装先を誤ると別プロジェクトを汚す可能性があるため）。

## メインエージェントの作業手順

### 1. 事前分析

- 実行計画書・③実装仕様書・規約ドキュメントを読み込む
- 実行計画書「6. 次工程（③コード生成）への申し送り」を確認する
- 対象Bounded Context・採用設計パターンを確認する

### 2. サブエージェント用プロンプトの作成

Agentツールで起動するサブエージェントに、以下を過不足なく含む自己完結型のプロンプトを渡してください（サブエージェントは今の会話の前提を共有していません）。

- 実装対象機能名・Bounded Context名・採用設計パターン
- 実行計画書・③実装仕様書・規約4点それぞれのファイルパス（サブエージェント自身に読ませる）
- 実行計画書「2. 作成ファイル一覧・順序」に記載の作成対象ファイル一覧と作成順序
- 実装先プロジェクトのルートパス
- 遵守事項: ③・実行計画書の内容を変更しない、規約に反しない、③に記載のない業務ルールを新設しない、スタブ・TODO・未実装を残さない、関数本体のロジックを完全に実装する
- テストコード（実行計画書「4. テストケース一覧」に対応するもの）も実装対象に含める旨
- 完了時に行うべきこと: 対象言語のビルド（例: `go build ./...`）・静的解析（例: `go vet ./...`）・テスト実行を行い、結果を報告すること

**1機能（Bounded Context）につきサブエージェント1体**とし、対象レイヤー全体（domain/application/infrastructure/presentationの該当レイヤー、Active Record/Transaction Script採用時はその構造）とテストコードを一括で担当させてください。レイヤー単位で複数サブエージェントに分割しないでください。

### 3. 実行と検証

- Agentツールでサブエージェントを起動する
- 完了後、メインエージェントは以下を確認する（サブエージェントの報告を鵜呑みにせず、必要であれば自身でビルド・テストを再実行して確認する）
  - 実行計画書「2. 作成ファイル一覧・順序」の全ファイルが実装されているか
  - struct/interface定義・メソッドシグネチャが③の記載と一致しているか
  - 規約に反する記述がないか
  - ビルド・静的解析・テストが通っているか
  - スタブ・TODO・未実装が残っていないか
- 問題がある場合、具体的な指摘内容を明記して同じサブエージェント（SendMessageで継続）に修正を依頼する。メインエージェントが直接修正コードを書かない

## 禁止事項

- メインエージェントが実装コードを直接記述する（サブエージェントへの委譲を経ない）
- 実行計画書・③・規約に反する実装をする
- ③に根拠のない業務ルール・実装詳細を無断で追加する
- スタブ・TODOコメント・未実装のまま完了とする
- テストコードの実装を省略する
- ビルド・テストの実行結果を確認せずに完了報告する

## 完了時

以下を満たしたら完了とし、次は `/impl:code-check` でセルフチェック＋目視確認に進む旨をユーザーに伝えてください。

- 実行計画書に記載された全ファイルが実装されている
- ビルド・静的解析がエラーなく通る
- テストコードが存在し、パスする
- 規約に反する記述がない
- ③に記載のない詳細を補った場合、その旨と判断理由が報告されている
