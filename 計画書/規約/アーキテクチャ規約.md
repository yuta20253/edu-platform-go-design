# アーキテクチャ規約

## 位置づけ

`規約/`配下には以下の4種類の規約がある。役割は明確に分離する。

|規約|扱う範囲|
|-|-|
|アーキテクチャ規約（本書）|レイヤー構成・依存方向・設計パターンごとの構造・Bounded Context構成・Context間連携・横断的関心事の置き場所・命名規則|
|コーディング規約|Go言語レベルの書き方（命名・エラー処理・並行処理・テストの書き方等）|
|Gorm規約|GORM固有の命名・タイムスタンプ・アソシエーション・Transaction・マイグレーション等のフレームワーク挙動|
|Gin規約|Gin固有のルーティング・ミドルウェア・Model Binding・エラーハンドリングミドルウェア等のフレームワーク挙動|

`Go移行・設計仕様書_自動生成プロンプト.md`（②）および`Go実装仕様書_自動生成プロンプト.md`（③）の「前提アーキテクチャ」節は、本書の内容を前提として簡潔に参照する。機能ごとの②③文書では、本書と矛盾する設計を採用しない。もし機能固有の事情で本書のルールから逸脱する必要がある場合は、その機能の②文書内で理由を明記する。

# 1. 全体方針

- Clean Architectureをベースとし、Bounded Context単位で業務領域を分割する
- DDDを目的として全機能にDomain Modelを強制しない。ドメインの複雑さに応じて、Transaction Script / Active Record / Domain Model / Event Sourcingを機能ごとに選択する（判断基準は②Go移行・設計仕様書_自動生成プロンプトの「設計パターン判断」節に従う）
- **採用した設計パターンに応じて、実装レイヤーの構造自体を変える。** 全パターンに同じフルレイヤー構成（domain/application/infrastructure/presentationのフルセット）を一律で適用しない。パターンごとの具体的な構造は「3. 設計パターンごとの構造適用方針」に従う
- フレームワーク（Gin・GORM）への依存は、採用パターンに応じた層（Infrastructure層、Active Recordの場合はStore）に閉じ込める
- Railsの実装構造（Controller/Service/Model/Form Object）を機械的に置き換えない。責務単位で再設計する

## ディレクトリ構成

本節はルート構成とContextディレクトリの命名のみを定める。Contextディレクトリの**内部**構成は採用パターンによって変わるため、「3. 設計パターンごとの構造適用方針」のツリーに従う（本節では再掲しない）。

個々のContextのディレクトリツリーを本書で列挙しない。Contextは追加・統合・改名されるため、全Contextを列挙すると本書が実態から乖離する。各Contextの具体的なファイル一覧は、その機能の③Go実装仕様書「2. ディレクトリ構成」で定める。

### ルート構成

|パス|役割|
|-|-|
|`cmd/api/`|エントリポイント。`main.go`のみを置き、業務ロジックを持たない（配線方法は「14. 依存関係の組み立て（DI配線）」）|
|`internal/<context>/`|Bounded Context単位の実装。1Contextにつき1ディレクトリ|
|`internal/config/`|環境変数・設定値の読み込み|
|`internal/db/`|DB接続の初期化と、`TransactionManager`のGORM実装（「11. Transaction実装パターン（TransactionManager）」）|
|`internal/middleware/`|全Contextが共通で使うGinミドルウェア（認証・認可・CORS・アクセスログ・エラーハンドリング）|
|`internal/jobqueue/`|`jobs`テーブルのGORMモデル・`JobPublisher`の実装・ポーリングワーカー（「13. 非同期ジョブ実行パターン（JobQueue）」）|
|`internal/shared/apperror/`|`AppError`インターフェースと共通のエラー型（「12. Error変換パターン（AppError）」）|
|`internal/shared/txmanager/`|`TransactionManager`インターフェース|
|`internal/shared/job/`|`JobPublisher`インターフェース|

Contextを束ねる中間ディレクトリ（`internal/context/`等）は設けず、Contextを`internal/`直下に並べる。

`internal/shared/`配下には、**複数のContextが共有することが確定した型のみ**を置く。1つのContextしか使わない型は、そのContext内に置く。`internal/shared/util`のように用途の分からない名前のディレクトリを作らない（コーディング規約「4. パッケージ設計」）。

インターフェースと、GORMに依存するその実装を同じpackageに置かない（`shared/txmanager`と`db`、`shared/job`と`jobqueue`を分けているのはこのためである）。同じpackageに置くと、インターフェースを参照するだけのApplication層が、package経由でGORMへ推移的に依存する。

### Contextディレクトリの命名

- ディレクトリ名は、Context名（kebab-case）の`-`を`_`に置き換えたものとする。**短縮・省略はしない**
  - `task-management` → `internal/task_management/`
  - `interview-request` → `internal/interview_request/`
  - `admin-account-management` → `internal/admin_account_management/`
- package名は、ディレクトリ名からアンダースコアを除いた連結形とする。コーディング規約「3. 命名規則」のとおり、package名にアンダースコアを使わないためである
  - `internal/task_management/` → `package taskmanagement`
  - `internal/study_log/` → `package studylog`
- 「8. 命名規約（アーキテクチャレベル）」の「package名はディレクトリ名と一致させる」は、この連結形への変換を許容する例外とする

ディレクトリ名・package名はContext名から機械的に決まるため、Context名とディレクトリ名の対応表を②③文書に持たせない。短縮形を使わないのはこのためである（`student-import`と`question-import`をいずれも`import`へ短縮すると衝突する、というような判断を機能ごとに行う必要がなくなる）。

Domain Model・Event Sourcingを採用したContextは、Contextディレクトリ直下に`.go`ファイルを置かず`domain/`等のサブディレクトリのみを持つ。この場合、Contextディレクトリ自体はpackageにならない。Active Record・Transaction Scriptを採用したContextは直下に`.go`ファイルを置くため、上記の連結形がそのpackage名になる。

### 1つのContextに複数の設計パターンが混在する場合

同一Contextを複数の機能が共有し、機能ごとに採用パターンが異なる場合がある（例：`announcement` Contextは、お知らせ機能がTransaction Script、教師お知らせ機能・管理者お知らせ管理機能がDomain Modelを採用している）。

この場合、Contextディレクトリの構成は**そのContextで採用されている最も複雑なパターンに合わせる**。単純なパターンを採用した機能も、そのContextの構造に従う。上の例では`announcement` Context全体をDomain Modelの構造とし、お知らせ機能の参照処理もusecase層を経由させる。

1つのContextディレクトリ内に、パターンの異なる構造（直下の`model.go`／`store.go`と`domain/`配下のEntityなど）を併存させない。同じデータに対する永続化の経路が2つになり、業務ルールの置き場所が決まらなくなるためである。

### 代表例

`announcement` Context（上記のルールにより、Domain Modelの構造を適用する）。

```
internal/announcement/
├── domain/
│   ├── entity/                   # Announcement, AnnouncementTarget
│   ├── valueobject/              # AnnouncementStatus, ScheduledAt 等
│   └── repository/               # Repository Interface
├── application/
│   ├── usecase/
│   └── dto/                      # Command / Query
├── infrastructure/
│   └── gormrepo/                 # Repository実装（package gormrepo）
├── presentation/
│   ├── handler/
│   ├── request/
│   ├── response/
│   └── routes.go
└── dependency.go                 # NewContext（「14. 依存関係の組み立て（DI配線）」）
```

Active Record採用Context・Transaction Script採用Context の構造は「3. 設計パターンごとの構造適用方針」のツリーのとおりで、`presentation/`配下の構成と`dependency.go`のみ上記と共通である。

機能で不要なディレクトリは作成しない。「層として必要だから」という理由で空のディレクトリを置かない。

同一Contextを複数の機能文書が共有し、UseCase・Handlerのstruct名が機能間で衝突する場合は、`application/`・`presentation/`の下を利用者ロール別のサブディレクトリ（`student/`・`teacher/`・`admin/`）に分割してよい。既存の③文書（面談機能と教師面談機能、管理者教員管理機能と教師教員管理機能）がこの分割を採用している。

# 2. レイヤー責務と依存方向（Domain Model / Event Sourcing）

本章の内容は、Domain Model・Event Sourcingを採用した機能に完全に適用される。Transaction Script・Active Recordを採用した機能は、本章のレイヤー分離・依存性逆転を行わない。詳細は「3. 設計パターンごとの構造適用方針」を参照する。

## 責務

|レイヤー|責務|
|-|-|
|Domain|業務ルール・状態・不変条件を表現する。Entity/Value Object/Repository Interface/Domain Service/Domain Event/Domain Errorを持つ|
|Application|UseCase単位で業務処理の流れを組み立てる。Domainを呼び出し、Repositoryを介して永続化を指示する。DTO（Command/Query）の入出力を扱う|
|Infrastructure|Repository Interfaceの実装、DB・外部サービス（メール・キャッシュ・キュー）との接続を担う|
|Presentation|HTTP入出力を担う。Request/Response DTOへの変換、Routingを扱う。業務ロジックは持たない|

## 依存方向

```
Presentation → Application → Domain
                    ↑
             Infrastructure
```

- DomainはApplication・Infrastructure・Presentationのいずれにも依存しない（Gin・GORMのimportを持たない）
- ApplicationはDomainに依存してよいが、Infrastructure・Presentationの具象実装には依存しない（Repositoryは常にDomain側で定義したInterface経由で利用する）
- InfrastructureはDomainのRepository Interfaceを実装する形でDomainに依存する（依存性逆転）
- PresentationはApplicationのUseCaseを呼び出す。Domainを直接操作しない

## 禁止事項

- DomainからGin/GORM/HTTPパッケージをimportする
- PresentationからRepository実装やGORMモデルを直接操作する
- UseCaseからHTTPリクエスト・レスポンスの型を直接扱う
- Repository実装に業務ルール判定を持たせる（②Go移行・設計仕様書_自動生成プロンプトの方針と同じ）

# 3. 設計パターンごとの構造適用方針

パターンが複雑になるほど、コード上の責務分離を増やす。逆に、複雑ではない業務領域に集約・Repository Interface・UseCase層といった分離を持ち込むと過剰設計になる。**設計の目的は複雑さの管理であり、複雑さのない領域に複雑さを管理するための構造を持ち込まない。**

## Transaction Script

対象: 一般・補完領域で、業務ルールが1〜2文で説明できる単純な処理（単純な一覧参照・集計・レポート生成・バッチ的処理等）。

構造:

- domain層は原則作らない。入力検証が必要な場合も、Value Object等の型は作らず、関数内のガード節で行う
- usecase層（struct・interface）は設けない。1つの業務操作を1つの関数として`application/`直下に置く
- Repository Interfaceは定義しない。DBアクセスは`infrastructure/`内の関数から直接行う
- Handlerは`application/`の関数を直接呼び出す

```
{context}/
├── application/
│   └── list_xxx.go        # 関数1つ = 1業務操作
├── infrastructure/
│   └── xxx_query.go       # DBアクセス関数
└── presentation/
    ├── handler/
    ├── response/
    └── routes.go
```

格上げの目安: 条件分岐や状態確認が増え、同じデータ構造を複数の関数で扱うようになった場合はActive Recordへ格上げを検討する。

## Active Record

対象: 補完領域でCRUDが中心、業務ルールがバリデーション程度、複雑な状態遷移がない機能。

構造:

- Repository InterfaceをDomain層に分離しない。永続化操作（Store）はEntity相当のstructと同じpackageに置く
- usecase層は設けない。HandlerがStoreを直接呼ぶ
- 依存関係の逆転は行わない（StoreがGORM/DBに直接依存してよい）

```
{context}/
├── model.go        # struct定義 + Validate()等のメソッド
├── store.go         # Save/FindByID/FindAll/Delete（DB直接操作）
└── presentation/
    ├── handler/
    ├── request/
    ├── response/
    └── routes.go
```

既存の②Go移行・設計仕様書のうちActive Recordを採用した機能（タスク管理機能・教師教員管理機能・管理者教員管理機能・目標管理機能等）は、「採用パターン」の判断自体は有効なまま維持する。ただしそれらの文書内でRepository／UseCaseという名称を用いて記載している箇所は、③Go実装仕様書を作成する際に本節の簡略構造へ読み替える。②文書そのものの再生成は行わない。

格上げの目安: バリデーション以上の複雑な業務ルール・状態遷移・複数集約にまたがるルールが発生した場合はDomain Modelへ格上げを検討する。

## Domain Model

対象: 中核領域で、複数の業務ルールがEntityに関連し、状態遷移ルールが存在する機能。

構造: 本書「2. レイヤー責務と依存方向」に記載の標準構成（値オブジェクト・Entity・集約・Repository Interfaceによる依存性逆転・usecase層のフルセット）を適用する。ディレクトリ構成は1章「ディレクトリ構成」の代表例のとおり。

## Event Sourcing

対象: 状態変化の追跡・監査・履歴再構築そのものが業務価値を持つ中核領域。

構造: Domain Modelの構成を基本とし、状態のスナップショットではなく発生したイベントの履歴を永続化するイベントストアをInfrastructure層に追加する。集約はイベントを適用して状態を再構築する。

### 本プロジェクトでの採用方針（2026-10時点の判断）

既存の全Contextで採用例はなく、採用を検討すべき機能も現時点では見当たらない。**イベントストアの具体的な設計方針は、採用する機能が実際に出てくるまで定めない。**

これは未決事項ではなく、意図的な判断である。イベントストアの設計（イベントの直列化形式・スナップショットの取得間隔・イベントスキーマの変更への追従方法等）は、どの集約に適用するかが決まらないと妥当性を判断できない。使われる見込みのない設計を先に規約へ書くと、実際に採用する機能が出た時点で、その機能の事情に合わない規約を根拠に設計を歪めることになる。

Event Sourcingを採用する機能が出た場合は、その機能の②文書で採用理由を明記し、同時に本節へイベントストアの設計方針を追記する。

## パターンの格上げ・格下げ

機能追加・仕様変更によって複雑さが増した場合、Transaction Script → Active Record → Domain Modelの順に構造を格上げできる。②文書の「採用パターン」判断を見直した場合は、③文書の構造も合わせて見直す。段階的な移行を前提とし、最初から全機能をDomain Modelで作らない。

## パターン別の観点比較

|観点|Transaction Script|Active Record|Domain Model|
|-|-|-|-|
|主役|関数|struct + Store|集約 + Repository Interface|
|業務ルールの置き場所|関数内|structのメソッド|集約内|
|DB依存|関数から直接|Storeが直接依存|Repository実装で分離（依存逆転）|
|usecase層|なし|なし|あり|
|Repository Interface|なし|なし|domain層に定義|
|適用領域|一般・補完|補完|中核|

# 4. Bounded Context構成

## Context分割基準

- 「誰が」「何を」「どの業務目的で」扱うかで分割する。Railsのディレクトリ構造（`Student::`, `Teacher::`, `Admin::`等の名前空間）をそのままContext境界にしない
- 同一データに対する参照専用の切り口（例：ダッシュボードでの集約表示）は、データを所有するContextとは別の「参照・集約専用Context」として切り出してよい。ただしその場合、業務ルール（作成・更新・状態遷移）は元のContextに残し、参照専用Contextは持たない
- 1つのContextが肥大化し、責務が「〇〇の一部だけ」に見えるようになった場合は分割を検討する。逆に、常に一体で扱われるデータ（例：Course/Unit）は無理に分割しない

## 命名規則

- Context名はkebab-case（例：`task-management`）とする。`internal/`配下のディレクトリ名・package名への変換規則は1章「ディレクトリ構成」で定めており、Context名から機械的に決まる。②③文書で対応関係を個別に明記する必要はない
- ②文書の「Context名」節には、kebab-caseのContext名のみを記載する。「お知らせ配信」「〇〇コンテキスト」のような日本語の補足を括弧で併記しない。1つのContextを複数の機能文書が共有する場合（例：`announcement`はお知らせ機能・教師お知らせ機能・管理者お知らせ管理機能の3文書が共有する）に、同じContextが文書間で別の名前に見えることを防ぐためである
- 日本語での補足が必要な場合は、「Context名」節の本文または「Contextの責務」節で説明する。いずれの場合も、実装上のディレクトリ・package名には反映しない

# 5. Context間連携ルール

- 他Contextのデータを利用する場合は、相手Contextが公開する参照手段（Domain Model採用時はRepository Interfaceの参照系メソッド、Active Record採用時はStoreの参照系メソッド、Transaction Script採用時は参照用の関数）を呼び出す
- 相手Contextの内部Entity・Value Object・Infrastructure実装に直接依存しない
- 状態変更を伴う連携（例：タスク完了に伴う目標の進捗更新）は、原則として呼び出し側の処理単位（UseCase、またはTransaction Script/Active Recordの場合は該当関数・Store操作）で両Context側の処理を順に呼び出す形にする。1トランザクションでの整合性が必要な場合は、Transaction設計（②の「14. Transaction設計」）で明示する
- 複数の処理へ波及する非同期通知が必要な場合のみ、Domain Eventの採用を検討する（②の「Domain Model採用基準」「Domain Event」節に準拠。安易に採用しない）
- Context間の循環依存は禁止する。依存が循環しそうな場合は、どちらかのContextの責務を見直す

# 6. データフロー

Domain Model / Event Sourcing採用時の基本形。

```
HTTP
 ↓
Handler
 ↓
Request DTO
 ↓
UseCase
 ↓
Repository Interface（Domain）
 ↓
Repository実装（Infrastructure / GORM）
 ↓
MySQL
```

戻りは逆順。

```
MySQL
 ↓
Repository実装
 ↓
Entity
 ↓
UseCase
 ↓
Response DTO
 ↓
JSON
```

Entityをそのままレスポンスとして返さず、必ずResponse DTOへ変換する。

Transaction Script採用時は「Handler → application関数 → infrastructure関数 → MySQL」、Active Record採用時は「Handler → Store → MySQL」と、経由するレイヤーがそのまま短縮される（3章参照）。

# 7. 横断的関心事の置き場所

|関心事|置き場所|方針|
|-|-|-|
|認証（本人確認）|Middleware|JWT等の検証、current userのcontext格納（`context.WithValue`の使用基準はコーディング規約「20. context.Context」に従う）。JWTをCookieで配布するため、CSRF対策はGin規約「5. CSRF対策」に従う|
|CORS|Middleware|フロントエンドが別オリジンで稼働する場合のみ必要。Cookie認証のため許可オリジンを明示列挙する（方針はGin規約「10. CORS」）。業務ロジック側では扱わない|
|認可（役割チェック）|Middleware|ロール（student/teacher/admin）レベルの粗い制御。実装はCasbin RBAC（Gin規約「4. 認可（Casbin RBAC）」）を用いる。所有権・業務権限の判定はCasbinの対象外とし、下記のとおりUseCase/Domainに置く|
|認可（所有権・業務権限）|UseCase / Domain（Domain Model採用時）、または該当関数・Store（Transaction Script/Active Record採用時）|「自分のデータか」「権限スコープ内か」等の業務的判定|
|入力チェック（型・必須・フォーマット）|Presentation（Request DTO）|HTTPレベルの入力検証|
|業務ルール検証|Domain（Domain Model採用時）、structのメソッド（Active Record採用時）、関数内（Transaction Script採用時）|状態遷移・整合性・業務制約|
|Transaction管理|UseCase、または該当関数・Store操作|業務処理の単位で開始・終了する（②の「14. Transaction設計」に従う）。Domain Model採用時の具体的な抽象化方法は「11. Transaction実装パターン（TransactionManager）」を参照|
|Error変換|Domain Error → Application Error → HTTP Response|各層で責務を分けて変換する（②の「17. Error設計」に従う）。Transaction Script/Active Record採用時はDomain Errorに相当する層がないため、関数・struct側で発生したエラーをApplication Error相当として扱う。Application Errorが実装すべき共通インターフェースとPresentation層での判定方法は「12. Error変換パターン（AppError）」を参照|
|ロギング|Middleware（アクセスログ）／Presentation（エラーログ、原則1箇所のみ）／Infrastructure（外部サービス呼び出し失敗のログ）|業務ロジックにロギング処理を持ち込まない。多重ログ防止・マスキング方針はコーディング規約「22. ロギング」に従う。ログレベルの決定方法は「12. Error変換パターン（AppError）」のAppError.LogLevel()を用いる|
|Context伝搬|UseCase・Repository・関数・Storeメソッドの第一引数|`context.Context`で受け渡す。`context.WithValue`で運んでよい値の範囲・キーの実装方法もコーディング規約「20. context.Context」に従う|

# 8. 命名規約（アーキテクチャレベル）

- package名はディレクトリ名と一致させ、`common`や`util`のような汎用的すぎる名前を避ける（詳細はコーディング規約「4. パッケージ設計」に従う）
- Repository InterfaceはDomain層に置き、実装側（Infrastructure）は`〇〇RepositoryImpl`のような接尾辞を付けず、Infrastructure側のpackage名（例：`gormrepo`）で区別する
- UseCaseは`動詞+対象+UseCase`の形式にする（例：`CreateTaskUseCase`, `ListTasksUseCase`）
- Active RecordのStoreは`〇〇Store`とし、メソッド名は`Save` / `FindByID` / `FindAll` / `Delete`等、用途が明確な動詞にする
- Transaction Scriptの関数は`動詞+対象`の形式にする（例：`ListRecentGoals`）
- Request/Response DTOは`〇〇Request` / `〇〇Response`の形式にする
- Domain Eventは過去形にする（例：`TaskCompleted`, `QuestionAnswered`）

# 11. Transaction実装パターン（TransactionManager）

Domain Model採用機能では、UseCaseが複数のRepositoryにまたがる処理を1トランザクションで実行する必要がある場合でも、UseCaseはGORMに直接依存できない（2章の依存方向・禁止事項）。この抽象化方法について②文書には定めがなく、既存の③文書（認証機能・問題解答機能・管理者管理者ユーザー機能・教師権限管理機能）が個別に同一の設計を「推測」として導出していたため、本規約で標準パターンとして定める。

## インターフェース

`internal/shared/txmanager/`に以下のインターフェースを定義する（1章「ディレクトリ構成」）。層としてはApplication層に属する。実装はGORMに依存するため`internal/db/`に置き、同じpackageに混在させない。

```go
type TransactionManager interface {
    WithinTransaction(ctx context.Context, fn func(ctx context.Context) error) error
}
```

## 実装

Infrastructure層でGORMの`*gorm.DB.Transaction`を用いて実装する。`fn`に渡す`ctx`にトランザクション用の`*gorm.DB`を保持させ、各Repository実装がその`ctx`からトランザクション用のDBコネクションを取り出して使用する（`context.WithValue`の使用基準はコーディング規約「20. `context.Context`」に従い、非公開の空struct型をキーに使う）。

```go
// Good
type ctxKeyTx struct{}

type transactionManager struct {
    db *gorm.DB
}

func NewTransactionManager(db *gorm.DB) TransactionManager {
    return &transactionManager{db: db}
}

func (m *transactionManager) WithinTransaction(ctx context.Context, fn func(ctx context.Context) error) error {
    return m.db.WithContext(ctx).Transaction(func(tx *gorm.DB) error {
        txCtx := context.WithValue(ctx, ctxKeyTx{}, tx)
        return fn(txCtx)
    })
}

// dbFromContext は、トランザクション中であればtxを、そうでなければ通常のdbを返す。
// Repository実装はこの関数経由でDBコネクションを取得する。
func dbFromContext(ctx context.Context, db *gorm.DB) *gorm.DB {
    if tx, ok := ctx.Value(ctxKeyTx{}).(*gorm.DB); ok {
        return tx
    }
    return db.WithContext(ctx)
}
```

```go
// Good（Repository実装側）
func (r *accountRepository) Create(ctx context.Context, a *domain.Account) error {
    m := fromDomain(a)
    return dbFromContext(ctx, r.db).Create(&m).Error
}
```

```go
// Bad
func (m *transactionManager) WithinTransaction(ctx context.Context, fn func(ctx context.Context) error) error {
    return m.db.Transaction(func(tx *gorm.DB) error {
        return fn(ctx) // txを渡さず元のctxをそのまま使う。Repository側がtxではなくdbを直接使ってしまい、トランザクションの外で実行される
    })
}
```

## 利用方法

UseCaseはコンストラクタ依存として`TransactionManager`を受け取り、複数Repositoryにまたがる処理を`WithinTransaction`のクロージャ内で実行する。読み取り専用UseCaseはトランザクションを使用しない。

```go
type CreateAdminUseCase struct {
    accountRepo AdminAccountRepository
    infoRepo    AdminPersonalInfoRepository
    txManager   TransactionManager
}

func (u *CreateAdminUseCase) Execute(ctx context.Context, cmd CreateAdminCommand) (Result, error) {
    var result Result

    err := u.txManager.WithinTransaction(ctx, func(ctx context.Context) error {
        // u.accountRepo.Create(ctx, ...)
        // u.infoRepo.Create(ctx, ...)
        return nil
    })

    return result, err
}
```

## 適用範囲

この標準パターンはDomain Model採用機能にのみ適用する。Active Record採用機能は、Gorm規約「0. 本プロジェクトでの採用方針」に従い、`db.WithContext(ctx).Transaction(func(tx *gorm.DB) error { ... })`をStoreメソッド内で直接使用する（3章「Active Record」の依存関係逆転を行わない方針のとおり）。Transaction Scriptは原則として単一操作のため、トランザクションが必要な場合はinfrastructure関数内で同様に直接呼び出す。

# 12. Error変換パターン（AppError）

7章「Error変換」の具体的な実装パターンを定める。DomainはHTTPステータス・ログレベルという概念を持たない（2章の依存方向のとおり、DomainはPresentationの関心事に依存しない）ため、これらはApplication層のエラー型が担う。

## インターフェース

`internal/shared/apperror/`に以下のインターフェースを定義する（1章「ディレクトリ構成」）。層としてはApplication層に属する。

```go
type AppError interface {
    error
    StatusCode() int
    LogLevel() slog.Level
}
```

## Domain Model採用時の変換

UseCaseは、Repository/Domainから返されたエラーを`errors.Is` / `errors.As`（コーディング規約「18. エラーハンドリング」参照）で判別し、`AppError`を実装した型に変換して返す。Domain Error自体にStatusCode/LogLevelを持たせない。

```go
// Good
func (uc *FindUserUseCase) Execute(ctx context.Context, id string) (*User, error) {
    user, err := uc.repo.FindByID(ctx, id)
    if err != nil {
        if errors.Is(err, domain.ErrUserNotFound) {
            return nil, apperror.NewNotFound("user not found")
        }

        return nil, apperror.NewInternal(err)
    }

    return user, nil
}
```

## Transaction Script / Active Record採用時の変換

7章のとおりDomain Errorに相当する層がないため、関数・struct（Store）が返すsentinel error・独自エラー型を、そのままApplication Error相当（`AppError`実装型）として扱う。関数・Store側で`AppError`を直接返してもよい。

## Presentation層での判定

Presentation層は、UseCase（またはTransaction Script/Active Recordの場合は該当関数・Store）から返されたエラーに対して`errors.As(err, &appErr)`を1回だけ呼び出し、`StatusCode()`でHTTPステータスを、`LogLevel()`でログレベルを決定する。個々のsentinel errorをHandler側で列挙して判定しない。

```go
// Good
func (h *Handler) FindUser(w http.ResponseWriter, req *http.Request) {
    ctx := req.Context()

    user, err := h.usecase.Execute(ctx, id)
    if err != nil {
        var appErr apperror.AppError
        if errors.As(err, &appErr) {
            h.logger.Log(ctx, appErr.LogLevel(), "failed to find user", "error", appErr)
            writeJSON(w, appErr.StatusCode(), ErrorResponse{Message: appErr.Error()})
            return
        }

        // AppErrorに変換されていない想定外のエラー
        h.logger.ErrorContext(ctx, "unexpected error", "error", err)
        writeJSON(w, http.StatusInternalServerError, ErrorResponse{Message: "internal server error"})
        return
    }

    writeJSON(w, http.StatusOK, toResponse(user))
}
```

```go
// Bad
func (h *Handler) FindUser(w http.ResponseWriter, req *http.Request) {
    _, err := h.usecase.Execute(req.Context(), id)
    if errors.Is(err, domain.ErrUserNotFound) {
        // ...
    } else if errors.Is(err, domain.ErrPermissionDenied) {
        // ...
    } else if errors.Is(err, domain.ErrValidationFailed) {
        // エラー種別が増えるたびにHandler側の分岐が増え続ける
    }
}
```

上記はレイヤー間の責務（Presentationで1回だけ判定する）を示す概念例である。本プロジェクト（Gin採用）では、この判定をHandlerごとに書くのではなく、Gin規約「8. エラーハンドリングミドルウェア」の集中エラーハンドリングミドルウェア1箇所に集約する。Handlerは`c.Error(err)`でエラーを登録するのみとする。

## 複数フィールドのバリデーションエラー

入力検証（コーディング規約「9. 関数・メソッド設計」の「入力検証とドメイン検証の責務分離」）で複数フィールドのエラーを同時に返す必要がある場合、`AppError`インターフェース自体は1つのエラーにつき1つの`StatusCode()`/`LogLevel()`しか持たないため、フィールド単位の詳細は別インターフェースで付加する。`AppError`本体のシグネチャは変更しない。

```go
type FieldError struct {
    Field   string `json:"field"`
    Message string `json:"message"`
}

// AppErrorに加えてフィールド詳細を持つ場合に実装する
type FieldErrorer interface {
    Fields() []FieldError
}

type ValidationError struct {
    Fields []FieldError
}

func (e *ValidationError) Error() string {
    return fmt.Sprintf("validation failed: %d field(s)", len(e.Fields))
}

func (e *ValidationError) StatusCode() int   { return http.StatusUnprocessableEntity }
func (e *ValidationError) LogLevel() slog.Level { return slog.LevelInfo }
```

Presentation層（Gin規約「8. エラーハンドリングミドルウェア」）は、`errors.As(err, &appErr)`で`AppError`を判定した後、追加で`errors.As(err, &fieldErr)`（`FieldErrorer`）を判定し、成功した場合のみレスポンスに`fields`を含める。`AppError`を実装するすべての型に`Fields()`を強制しない。

# 13. 非同期ジョブ実行パターン（JobQueue）

CSVインポート処理・お知らせのスケジュール公開・パスワードリセットメール送信など、HTTPリクエストの応答を待たずにバックグラウンドで実行する処理が複数機能で必要になる。この実装基盤について②文書には定めがなく、既存の③文書（管理者問題インポート機能）は「具体的なメッセージング基盤（SQS・Redis Streams・Kafka等）の選定は本書のスコープ外とする」と明記して抽象インターフェース（`event.Publisher`）の定義に留めていた。本規約では、この抽象を具体化する標準実装を定める。

## 基盤の選定

本プロジェクトの前提（Gin・GORM・MySQLのみ、19機能規模）を踏まえ、Redis・Kafka等の新規メッセージブローカーは導入しない。MySQLの`jobs`テーブルとポーリングワーカーによる、追加インフラ不要の実装を標準とする。

## 処理の分類

|分類|特徴|対象例|
|-|-|-|
|確実に実行したい処理|プロセス再起動後も再実行が必要、リトライが必要|CSVインポート処理、お知らせのスケジュール公開|
|ベストエフォートで良い処理|失敗時は次の機会に委ねてよい、再送要求が容易|パスワードリセットメール送信|

## インターフェース

`internal/shared/job/`に以下のインターフェースを定義する（1章「ディレクトリ構成」）。層としてはApplication層に属する。実装とワーカーはGORMに依存するため`internal/jobqueue/`に置き、同じpackageに混在させない。

```go
type JobPublisher interface {
    Publish(ctx context.Context, jobType string, payload any, runAfter time.Time) error
}
```

`runAfter`に現在時刻を渡せば即時実行相当になり、未来の時刻を渡せばスケジュール実行（お知らせの`scheduled`→`published`遷移等）になる。

## 確実に実行したい処理: `jobs`テーブル + ポーリングワーカー

Infrastructure層に以下のGORMモデルで`jobs`テーブルを持つ。

```go
type Job struct {
    ID          uint
    Type        string
    Payload     string // JSON文字列（json.Marshal/Unmarshalで扱う。datatypes.JSON等の追加型は導入しない）
    Status      string // pending / processing / completed / failed
    Attempts    int
    MaxAttempts int
    RunAfter    time.Time
    CreatedAt   time.Time
    UpdatedAt   time.Time
}
```

`JobPublisher`の実装は、トリガーとなる業務データの書き込みと同一トランザクション内で`jobs`テーブルへの`INSERT`を行う（「11. Transaction実装パターン（TransactionManager）」の`WithinTransaction`スコープ内で呼び出す。Transactional Outboxパターン）。これにより「業務データは保存されたがジョブが登録されない」「ジョブは登録されたが業務データが保存されない」という不整合を防ぐ。

ワーカーは`main.go`から起動する常駐goroutineとし、一定間隔で`status = 'pending' AND run_after <= ?`を満たす`jobs`行をポーリングし、`type`に応じて登録済みハンドラを呼び出す。処理成功時は`status`を`completed`に、失敗時は`attempts`をインクリメントし`max_attempts`未満なら`pending`に戻す（次回ポーリングで再試行）、`max_attempts`に達したら`failed`とする。

```go
// main.go（起動イメージ）
worker := jobqueue.NewWorker(db, logger, jobqueue.HandlerMap{
    "question_import":       questionImportHandler,
    "announcement_publish":  announcementPublishHandler,
})

go worker.Run(ctx, 5*time.Second) // 5秒間隔でポーリング
```

## ベストエフォートで良い処理: goroutine起動

`jobs`テーブルを経由せず、Handlerまたは UseCase から直接goroutineを起動してよい。失敗時のリトライはユーザーの再操作（例: パスワードリセットの再申請）に委ねる。

```go
// Good
go func() {
    ctx := context.Background() // リクエストの生存期間に紐づけない

    if err := mailer.SendResetPasswordEmail(ctx, user.Email, token); err != nil {
        logger.ErrorContext(ctx, "failed to send reset password email", "error", err)
    }
}()
```

無制限にgoroutineを起動しない。同時実行数が問題になりうる処理（大量送信等）は、確実に実行したい処理側（`jobs`テーブル）に倒す。

## 適用範囲と既知の制約

このワーカーはアプリケーションプロセス内の単一goroutineとして動作する前提である。

### ジョブの二重実行防止

単一インスタンス・単一ワーカーgoroutineであっても、**ジョブの取得は最初から排他制御付きで実装する**。排他制御のない取得（`status = 'pending'`の行を`SELECT`してから`UPDATE`する）は、インスタンスを2つに増やした瞬間に同じジョブが二重実行される。CSVインポートのような副作用のある処理が二重に走ると、後から原因を特定しづらい不整合を生むため、水平スケーリングの予定が立ってから対応するのでは遅い。

取得は、トランザクション内で`SELECT ... FOR UPDATE SKIP LOCKED`により行をロックし、同じトランザクションで`status`を`processing`へ更新してからコミットする。`SKIP LOCKED`により、他のワーカーがロック中の行は待たずに飛ばして次の行を取得する（MySQL 8.0以降で利用できる）。

```go
// Good
func (w *Worker) fetch(ctx context.Context, limit int) ([]Job, error) {
    var jobs []Job

    err := w.db.WithContext(ctx).Transaction(func(tx *gorm.DB) error {
        if err := tx.Clauses(clause.Locking{Strength: "UPDATE", Options: "SKIP LOCKED"}).
            Where("status = ? AND run_after <= ?", StatusPending, time.Now()).
            Order("run_after").
            Limit(limit).
            Find(&jobs).Error; err != nil {
            return err
        }

        if len(jobs) == 0 {
            return nil
        }

        ids := make([]uint, 0, len(jobs))
        for _, j := range jobs {
            ids = append(ids, j.ID)
        }

        // ロックを保持したまま processing へ遷移させ、コミット後は他ワーカーの取得対象から外れる
        return tx.Model(&Job{}).Where("id IN ?", ids).
            Updates(map[string]any{"status": StatusProcessing, "attempts": gorm.Expr("attempts + 1")}).Error
    })

    return jobs, err
}
```

```go
// Bad
// SELECTとUPDATEが別トランザクションのため、2つのワーカーが同じ行を取得できる
var jobs []Job
db.Where("status = ?", StatusPending).Find(&jobs)
db.Model(&Job{}).Where("id IN ?", ids).Update("status", StatusProcessing)
```

`attempts`のインクリメントを取得時に行うのは、処理中にプロセスが落ちた場合でも試行回数が記録され、`max_attempts`による打ち切りが機能するようにするためである。処理中のまま放置された`processing`の行を`pending`へ戻す回収処理（一定時間`updated_at`が更新されていない行を対象とする）は、ワーカー起動時とポーリングのたびに行う。

この実装により、ワーカーを複数インスタンスで動かしても二重実行は起きない。ただし1つのジョブの処理時間がロックの保持時間に比例して長くなる設計は避け、ジョブ1件あたりの処理は冪等に書く（同じジョブが再試行されても結果が変わらないようにする）。

既存の③文書（管理者問題インポート機能等）で「メッセージング基盤の選定はスコープ外」としていた箇所は、次回更新時に本節の標準実装へ置き換える。

# 14. 依存関係の組み立て（DI配線）

UseCase・Repository・TransactionManager等、コンストラクタ注入（コーディング規約「6. 構造体・インターフェース設計」の`NewXxx`）で組み立てる依存関係を、実際にどこでどう配線するかを定める。

## 配線方法

`google/wire`等のコード生成DIツールは導入しない。本プロジェクトの規模（19機能）では、コード生成の学習・ビルドコストに見合わないため、`main.go`とContextごとの組み立て関数による手動配線とする。

## Context単位の組み立て関数

各Contextは、そのContext内の依存関係を組み立てる関数を1つ持つ。関数名は`NewContext`とし、Contextディレクトリ直下の`dependency.go`に置く（1章「ディレクトリ構成」）。この関数はDB接続・ロガー等の共通依存を受け取り、Repository → UseCase → Handlerの順に生成して返す。

```go
// internal/announcement/dependency.go（Domain Model採用Context）
package announcement

func NewContext(db *gorm.DB, logger *slog.Logger) *Context {
    txManager := appdb.NewTransactionManager(db) // internal/db
    announcementRepo := gormrepo.NewAnnouncementRepository(db)

    createUseCase := usecase.NewCreateAnnouncementUseCase(announcementRepo, txManager)
    listUseCase := usecase.NewListAnnouncementsUseCase(announcementRepo)

    h := handler.New(createUseCase, listUseCase)

    return &Context{Handler: h}
}
```

Active Record・Transaction Scriptを採用したContextは、usecase層を持たないため、Store・関数をHandlerへ直接渡す。

```go
// internal/task_management/dependency.go（Active Record採用Context）
package taskmanagement

func NewContext(db *gorm.DB, logger *slog.Logger) *Context {
    taskStore := NewTaskStore(db) // 同一package（3章「Active Record」）

    h := handler.New(taskStore)

    return &Context{Handler: h}
}
```

## `main.go`での配線

`main.go`は、コーディング規約「4. パッケージ設計」の`init`関数方針のとおりConfig読み込み・DB接続等の共通依存を組み立てた後、各Contextの`NewContext`を呼び出し、Gin規約「2. ルートグルーピング」に従ってルートを登録する。Context間の生成順序に依存関係がある場合を除き、順序を問わない。

```go
// cmd/api/main.go
func main() {
    cfg, err := config.Load()
    if err != nil {
        log.Fatal(err)
    }

    logger := newLogger(cfg)

    db, err := appdb.Connect(cfg) // internal/db
    if err != nil {
        log.Fatal(err)
    }

    router := gin.New()
    // internal/middleware（1章「ディレクトリ構成」）
    router.Use(
        middleware.CORS(cfg.AllowedOrigins), // Gin規約「10. CORS」
        middleware.AccessLogger(logger),
        middleware.ErrorHandler(logger),
    )

    api := router.Group("/api/v1")

    announcementCtx := announcement.NewContext(db, logger)
    announcementCtx.RegisterRoutes(api)

    taskCtx := taskmanagement.NewContext(db, logger)
    taskCtx.RegisterRoutes(api)

    // ...

    router.Run(":" + cfg.Port)
}
```

## 禁止事項

* パッケージ変数・`init`関数による暗黙的な依存の組み立て（コーディング規約「4. パッケージ設計」の`init`関数方針のとおり）
* Context間で直接依存関係を注入し合う配線（5章「Context間連携ルール」のとおり、Context間はRepository/Store/関数の参照手段のみを介して連携する。依存関係の組み立て自体を他Contextと共有しない）

# 15. API規約（レスポンス形式・ページネーション・URL・クエリパラメータ）

②の「API互換」方針に従い、Rails現行APIの形式を維持する。フロントエンドの修正を不要にするためである。機能固有の事情でこの規約から逸脱する場合は、その機能の②文書内で理由を明記する。

## 成功レスポンス

|種別|形式|
|-|-|
|単体（取得・作成・更新）|envelopeなしのJSONオブジェクト。Rails現行がリソース名でラップしている機能（例：教員作成の`{"teacher": {...}}`）は、②の互換方針に従いそのまま維持する|
|一覧（ページネーションあり）|`{"<リソース名の複数形>": [...], "meta": {...}}`|
|一覧（ページネーションなし。マスタ参照等）|JSON配列|
|処理結果のみを返す操作|`{"message": "..."}`|

- 汎用の`{"data": ...}`envelopeは採用しない（Rails現行と非互換になるため）
- 処理結果のみを返す操作のステータスは、作成は201、非同期処理の受付は202、それ以外は200とする

一覧（ページネーションあり）の例:

```json
{
  "students": [ ... ],
  "meta": { "current_page": 1, "total_pages": 5, "total_count": 42, "per_page": 10 }
}
```

## エラーレスポンス

- 形式は`{"errors": ["メッセージ", ...]}`とする。エラーが1件でも配列で返す
- ステータスへの変換は「12. Error変換パターン（AppError）」に従う。Rails現行の主な対応は、入力・業務検証エラー=422、楽観的排他制御の競合=409である
- Rails現行が上記と異なるステータスを返す機能（例：住所検索の`prefecture_id`未指定は400）は、互換を優先し、②で明記した上で維持する

## ページネーション

- クエリパラメータは`page`と`per_page`とする。0以下や数値以外の値は無視し、既定値を用いる
- `per_page`の既定値と上限は、機能ごとに②で定める
- 件数などの情報は、一覧レスポンス最上位の`meta`に含める。項目は`current_page` / `total_pages` / `total_count` / `per_page`の4つとする

## URL

- ベースは`/api/v1/`とする。利用者ロール固有のAPIは`/api/v1/{student|teacher|admin}/...`、ロールを問わないAPIはロール名を含めず`/api/v1/...`とする
- リソース名はsnake_caseの複数形とする（例：`interview_requests`）。1つしか存在しないリソースは単数形とする（例：`dashboard` / `account_link`）
- 親子関係のあるリソースは`/親/:親のid/子`とネストする（例：`/interview_requests/:id/messages`）。階層の深さはRails現行を維持する
- 作成・更新・削除で表せない操作は、対象の後ろに動詞を置く（例：`/announcements/:id/publish`、`/import_histories/:id/export`）

## クエリパラメータ

|用途|名前|備考|
|-|-|-|
|ページ|`page` / `per_page`|「ページネーション」参照|
|キーワード検索|`keyword`|Rails現行で`q`を使っている機能は`keyword`に揃える。フロントエンドの修正が必要になる|
|状態での絞り込み|`status`||
|期間での絞り込み|`from` / `to`||
|並び替え|`sort`（列名）と`order`（`asc` / `desc`）|Rails現行のとおり2つを組で使う。許可する列名と既定値は、機能ごとに②で定める|

上記以外の絞り込みパラメータは、Rails現行の名前を維持し、機能ごとに②で定める。
