## 1. 基本方針

* Go 標準の書き方を優先する
* 独自ルールを増やしすぎない
* `gofmt` による自動フォーマットを必須とする
* `golangci-lint` などの静的解析ツールを CI で必須とする
* 可読性を優先し、過度な抽象化を避ける
* エラーを無視しない
* 不要なコメント・不要なコードを増やさない

---

## 2. コードフォーマット

基本的に手動でフォーマットしない。

以下のいずれかを使用する。

```bash
# 単一ファイルをフォーマット
go fmt main.go

# パッケージ全体をフォーマット
go fmt ./...

# gofmt を使用
gofmt -w *.go

# goimports を使用（インポートを自動管理）
goimports -w *.go
```

すべての Go コードは `gofmt` でフォーマットする。

### Good

```bash
gofmt -w *.go
```

### Bad

```go
// 手動でインデントや空白を調整したコードをそのままコミットする
func main() {
fmt.Println("Hello")
}
```

## 3. 命名規則

Go では大文字・小文字によって公開・非公開を表現する。

複数語からなる識別子には、アンダースコア区切り（snake_case）ではなく`MixedCaps`（公開識別子）または`mixedCaps`（非公開識別子）を使用する。この原則はパッケージ名・変数・関数・定数など、すべての識別子に共通する。

```go
// Good
var maxRetryCount int

func parseUserInput() {}
```

```go
// Bad
var max_retry_count int

func parse_user_input() {}
```

### パッケージ名

小文字の単語で簡潔にする。

### Good

```go
package httputil
```

### Bad

```go
package HTTPUtil
```

`util` や `common` のような一般的すぎるパッケージ名は避ける。

### Good

```go
package httputil
```

### Bad

```go
package util
```

```go
package common
```

### 公開・非公開

公開する識別子は先頭を大文字にする。

```go
// Good

// 公開関数
func NewClient() *Client {}

// 非公開関数
func parseURL(url string) error {}
```

```go
// Bad

// 公開する関数を小文字で定義している
func newClient() *Client {}

// 非公開関数を大文字で定義している
func ParseURL(url string) error {}
```

### 定数

キャメルケースを使用し、アンダースコアは使用しない。

```go
// Good
const MaxRetryCount = 3
const defaultTimeout = 30
```

```go
// Bad
const MAX_RETRY_COUNT = 3
const default_timeout = 30
```

### 定数のグループ化と `iota`

関連する定数は `const` ブロックにまとめ、連番の列挙には `iota` を使用する。

```go
// Good
type Status int

const (
    StatusPending Status = iota
    StatusActive
    StatusClosed
)
```

```go
// Bad
const StatusPending = 0
const StatusActive = 1
const StatusClosed = 2
```

### インターフェース

単一メソッドのインターフェースには `-er` 接尾辞を使用する。

```go
// Good
type Reader interface {
    Read([]byte) (int, error)
}

type Writer interface {
    Write([]byte) (int, error)
}
```

```go
// Bad
type FileReader interface {
    Read([]byte) (int, error)
}

type FileWriter interface {
    Write([]byte) (int, error)
}
```

## 4. パッケージ設計

### パッケージ名

パッケージ名は簡潔で意味のあるものにする。

```go
// Good

// Package httputil は HTTP の共通ユーティリティを提供します。
package httputil
```

```go
// Bad

// パッケージ名から用途が分かりにくい
package common
```

### パッケージ名との重複（stutter）を避ける

エクスポートする識別子は、呼び出し側で`パッケージ名.識別子`という形で参照されることを前提に命名する。パッケージ名と同じ単語を識別子名に繰り返さない。

```go
// Good
package task

type Task struct{}

func New() *Task { return &Task{} }

// 呼び出し側: task.Task{}, task.New()
```

```go
// Bad
package task

type TaskInfo struct{}

func NewTask() *TaskInfo { return &TaskInfo{} }

// 呼び出し側: task.TaskInfo{}, task.NewTask() のように単語が重複する
```

### パッケージの分割基準

1パッケージ内のファイル数が増えすぎ、関連の薄いファイルが混在するようになった場合は、サブパッケージへの分割を検討する。分割の際は、アーキテクチャ規約「2. レイヤー責務と依存方向」「3. 設計パターンごとの構造適用方針」の考え方に従う（具体的なディレクトリ構成は未定）。

```go
// Good
internal/task/
├── application/
│   ├── create_task_usecase.go
│   └── list_tasks_usecase.go
└── infrastructure/
    └── task_repository.go
```

```go
// Bad
internal/task/
└── everything.go // UseCase・Repository実装・DTOがすべて1ファイルに集約されている
```

逆に、ファイル数が少ない段階から先回りしてサブパッケージへ分割しない。

### インポート

インポートは以下の順序でグループ化する。

1. 標準ライブラリ
2. プロジェクト・サードパーティパッケージ
3. Protocol Buffer
4. サイドエフェクトのみのインポート

```go
// Good
import (
    "fmt"
    "net/http"

    "github.com/gin-gonic/gin"

    "myproject/internal/config"
)
```

```go
// Bad
import (
    "github.com/gin-gonic/gin"
    "fmt"
    "myproject/internal/config"
    "net/http"
)
```

### インポートのリネーム

基本的にはインポートしたパッケージをリネームしない。

ただし、以下の場合はリネームしてよい。

* 名前が衝突する場合
* パッケージ名が分かりにくい場合

```go
// Good
import (
    foosvcpb "path/to/package/foo_service_go_proto"
)
```

リネームする場合は、アンダースコアや大文字を使用せず、コードベース全体で一貫した名前を使用する。

```go
// Good
import (
    foosvcpb "path/to/package/foo_service_go_proto"
)
```

```go
// Bad
import (
    FooSvcPB "path/to/package/foo_service_go_proto"
)
```

```go
// Bad
import (
    foo_svc_pb "path/to/package/foo_service_go_proto"
)
```

### `import .`

`import .` は使用しない。

```go
// Bad
import (
    "bar/testutil"
    . "foo"
)

var myThing = Bar()
```

```go
// Good
import (
    "bar/testutil"
    "foo"
)

var myThing = foo.Bar()
```

### `import _`

副作用のみを目的とした blank import は、原則として `main` パッケージまたは必要なテストファイルでのみ使用する。

ライブラリパッケージでは避ける。

```go
// Good
package main

import (
    _ "github.com/go-sql-driver/mysql"
)
```

```go
// Bad
package config

import (
    _ "github.com/go-sql-driver/mysql"
)
```

### `init` 関数

`init`関数は、変数宣言だけでは表現できない初期化処理（複雑な検証・計算を伴う初期化等）に限って使用する。DIの配線・設定の読み込みのように依存関係や実行順序を明示したい処理には使わず、`main`関数または明示的なセットアップ関数の中でコンストラクタ注入によって組み立てる（アーキテクチャ規約「11. Transaction実装パターン（TransactionManager）」の`TransactionManager`と同様、依存はコンストラクタで受け渡す）。

```go
// Good
func main() {
    cfg := loadConfig()
    db := connectDB(cfg)
    txManager := infrastructure.NewTransactionManager(db)
    createTaskUseCase := usecase.NewCreateTaskUseCase(repo, txManager)
    // ...
}
```

```go
// Bad
var db *gorm.DB

func init() {
    // DBコネクションの確立や設定読み込みをinitで行うと、
    // 実行順序が暗黙的になりテストで差し替えづらくなる
    db = connectDB()
}
```

### 設定値（Config）の読み込み

設定値は環境変数から読み込む。ローカル開発では`.env`ファイルを用いて環境変数を補う（配置ディレクトリはアーキテクチャ規約のディレクトリ構成が確定次第定める）。設定用の構造体・読み込み関数は共通コード置き場となるパッケージに置き、`main`関数の先頭で1回だけ読み込んで、以降は明示的な引数・コンストラクタ注入で各層に渡す（アーキテクチャ規約「14. 依存関係の組み立て（DI配線）」参照）。

```go
// Good
// internal/shared/config/config.go
type Config struct {
    DBHost   string
    DBPort   int
    Port     string
    LogLevel string
}

func Load() (*Config, error) {
    port, err := strconv.Atoi(os.Getenv("DB_PORT"))
    if err != nil {
        return nil, fmt.Errorf("DB_PORTの読み込みに失敗しました: %w", err)
    }

    return &Config{
        DBHost:   os.Getenv("DB_HOST"),
        DBPort:   port,
        Port:     os.Getenv("PORT"),
        LogLevel: os.Getenv("LOG_LEVEL"),
    }, nil
}
```

```go
// Bad
var Cfg Config // パッケージ変数として公開し、どこからでも参照・上書きできてしまう

func init() {
    Cfg = loadConfigSomehow()
}
```

環境（開発・ステージング・本番）ごとに設定ファイルを複数用意する方式は採用せず、環境変数の値のみで切り替える。

### Goバージョンの指定

`go.mod`の`go`ディレクティブで、プロジェクトが要求する最低Goバージョンを固定する。CIのビルド・テストで使用するGoのバージョンは、`go.mod`の値と一致させる。

```go
// Good
// go.mod
module myproject

go 1.24
```

`go.mod`の`go`ディレクティブより新しいGoの言語機能（新しい標準ライブラリ関数・構文）を使用しない。バージョンを引き上げる場合は、`go.mod`の更新とCI設定の更新を同一の変更内でセットで行う。

```go
// Bad
// go.mod では go 1.21 のままなのに、コード側で1.22以降の言語仕様（forループ変数のセマンティクス変更等）に暗黙に依存する
```

パッチバージョン（`1.24.x`）はCI・開発環境間で完全に一致させる必要はないが、マイナーバージョン（`1.24`）は`go.mod`の値を正とする。

## 5. ファイル設計

### ファイルの長さ

1ファイルは目安として150行以内に収める（Rails現行コードの平均行数（テスト除く、約100行）に、Go側の型定義・明示的なエラー処理による増分を加味した水準）。超える場合は責務ごとに別ファイルへ分割する。

### 1ファイル1責務

1ファイルには1つの主要な型・1つのユースケースを対応させる。ファイル名はその中身を表す名前にする。

```go
// Good
// create_task_usecase.go
package usecase

type CreateTaskUseCase struct{ /* ... */ }

func (uc *CreateTaskUseCase) Execute(ctx context.Context, cmd CreateTaskCommand) (*Task, error) {
    // ...
    return nil, nil
}
```

```go
// Bad
// usecase.go
package usecase

type CreateTaskUseCase struct{ /* ... */ }
type UpdateTaskUseCase struct{ /* ... */ }
type DeleteTaskUseCase struct{ /* ... */ }
type ListTasksUseCase struct{ /* ... */ }
// 関連の薄い複数のUseCaseが1ファイルに詰め込まれている
```

Transaction Script採用時の「動詞+対象」関数（例：`ListRecentGoals`）のように厳密に1関数1ファイルとまではしなくてよいが、無関係な処理を1ファイルに混在させない。

### ファイルの分割タイミング

以下のいずれかに該当する場合、ファイルを分割する。

* ファイルの行数が目安（150行）を超えた
* 1ファイルの中に、互いに呼び出し関係のない複数の型・関数群が存在する
* テストファイルが肥大化し、テスト対象の粒度が読み取りにくくなった

```go
// Good
internal/task/infrastructure/repository/
├── task_repository.go       // TaskRepositoryのCRUD
├── task_query.go            // 検索・フィルタリング専用のクエリ
└── task_repository_test.go
```

```go
// Bad
internal/task/infrastructure/repository/
└── task_repository.go       // CRUD・検索・集計・エクスポート等、無関係な処理が1ファイル300行超に詰め込まれている
```

## 6. 構造体・インターフェース設計

Goにクラスはないが、structとそれに紐づくメソッド群が実質的な「クラス相当」の単位となる。

### フィールド数の上限

structのフィールドは目安として7つまでとする。それを超える場合は、意味のあるまとまりで別のstructに分割することを検討する。

```go
// Good
type Task struct {
    Name     string
    DueDate  time.Time
    Assignee Assignee
}

type Assignee struct {
    UserID uint
    Name   string
}
```

```go
// Bad
type Task struct {
    Name           string
    DueDate        time.Time
    AssigneeID     uint
    AssigneeName   string
    AssigneeRole   string
    CreatedByID    uint
    CreatedByName  string
    Status         string
    Priority       int
    // ...フィールドが際限なく増えている
}
```

### メソッド数と責務（God Object回避）

1つのstructが持つメソッドが増えすぎ、異なる関心事（例：バリデーション・永続化・通知）を1つの型が担うようになった場合は、責務ごとに型を分割する。

```go
// Bad
type Task struct {
    // ...フィールド
}

func (t *Task) Validate() error              { /* ... */ return nil }
func (t *Task) Save(db *gorm.DB) error        { /* 永続化の関心事 */ return nil }
func (t *Task) SendNotification() error       { /* 通知の関心事 */ return nil }
func (t *Task) ExportToCSV() ([]byte, error)  { /* エクスポートの関心事 */ return nil, nil }
func (t *Task) RenderHTML() (string, error)   { /* 表示整形の関心事 */ return "", nil }
// Taskが業務ルール・永続化・通知・エクスポート・表示のすべてを担っている
```

```go
// Good
type Task struct {
    // ...フィールド
}

func (t *Task) Validate() error { /* ... */ return nil } // 業務ルールのみ

type TaskStore struct{ /* ... */ }

func (s *TaskStore) Save(ctx context.Context, t *Task) error { /* ... */ return nil } // 永続化の関心事を分離

type TaskNotifier struct{ /* ... */ }

func (n *TaskNotifier) NotifyCompleted(ctx context.Context, t *Task) error { /* ... */ return nil } // 通知の関心事を分離
```

### インターフェースのメソッド数

インターフェースは3メソッド以内を目安にする。それを超える場合は、利用側が実際に必要とするメソッドだけを持つ小さなインターフェースに分割する。

```go
// Good
type Reader interface {
    Read([]byte) (int, error)
}

type Writer interface {
    Write([]byte) (int, error)
}
```

```go
// Bad
type ReadWriteCloserFlusherSeeker interface {
    Read([]byte) (int, error)
    Write([]byte) (int, error)
    Close() error
    Flush() error
    Seek(int64, int) (int64, error)
    // 利用側が実際には一部のメソッドしか使わない
}
```

### 構造体埋め込み（embedding）

埋め込みは共通のふるまいを再利用する場合にのみ使用し、単なるフィールドの共有には通常のフィールドとして持たせる。

```go
// Good
type Base struct {
    ID        uint
    CreatedAt time.Time
}

type Task struct {
    Base
    Name string
}
```

```go
// Bad
type Task struct {
    Config Config // 埋め込みではなく明示フィールドにすべき単なる設定値
}
```

埋め込みによって意図しないメソッドが公開される場合があるため、埋め込み元の公開APIが妥当かどうかを確認する。

複数の型を埋め込み、同名メソッドが衝突する場合はコンパイルエラーにならず、呼び出し時にのみ曖昧参照としてエラーになる（同じ深さで衝突した場合）。このような衝突が生じる設計は避ける。

```go
// Bad
type Logger struct{}

func (Logger) String() string { return "logger" }

type Formatter struct{}

func (Formatter) String() string { return "formatter" }

type Report struct {
    Logger
    Formatter
}

// report.String() は「ambiguous selector」としてコンパイルエラーになる
```

```go
// Good
type Report struct {
    Logger
    Formatter
}

// 曖昧さを避け、明示的にどちらのStringか分かる名前でラップする
func (r Report) LogString() string {
    return r.Logger.String()
}
```

### コンストラクタ（`NewXxx`）

外部からの生成時に不変条件（必須フィールド・初期値）がある構造体は、フィールドを直接埋めるのではなく`NewXxx`コンストラクタ関数を用意する。

```go
// Good
func NewTask(name string, dueDate time.Time) (*Task, error) {
    if name == "" {
        return nil, errors.New("name is required")
    }

    return &Task{Name: name, DueDate: dueDate}, nil
}
```

```go
// Bad
task := &Task{} // 必須フィールドが未設定のまま生成できてしまう
task.Name = ""
```

単純なDTOなど、不変条件を持たない構造体には`NewXxx`を強制しない（9章「構造体リテラル」に従う）。

### `Stringer`実装時の注意

`fmt.Stringer`（`String() string`メソッド）を実装する際、メソッド内で`%v`のようにレシーバー自身を介して自分自身をフォーマットすると無限再帰に陥る。個々のフィールドを指定してフォーマットする。

```go
// Good
func (u User) String() string {
    return fmt.Sprintf("User(%s)", u.Name)
}
```

```go
// Bad
func (u User) String() string {
    return fmt.Sprintf("%v", u) // %v が再度 String() を呼び出し無限再帰になる
}
```

## 7. インターフェース

インターフェースは、実装するパッケージではなく、**利用するパッケージ側**で定義する。

```go
// Good

package consumer

type Thinger interface {
    Thing() bool
}

func Foo(t Thinger) string {
    // ...
}
```

```go
// Bad

// 実装側で利用者のためのインターフェースを定義している
package producer

type Thinger interface {
    Thing() bool
}

type Thing struct {
    // ...
}
```

実装側は可能な限り具象型を返す。

```go
// Good
func NewClient() *Client {
    return &Client{}
}
```

```go
// Bad
func NewClient() ClientInterface {
    return &Client{}
}
```

### 引数は必要最小限のインターフェースを受け取る

関数の引数は、実際に必要な操作だけを持つ最も一般的な型（インターフェース）を受け取る。具象型や、実際には使わないメソッドまで含む広いインターフェースを要求すると、テスト時の差し替えやすさ・呼び出し側の柔軟性が失われる。

```go
// Good
func CopyData(w io.Writer, r io.Reader) error {
    _, err := io.Copy(w, r)
    return err
}
```

```go
// Bad
func CopyData(w *os.File, r *os.File) error {
    // io.Writer/io.Readerで十分なのに具象型 *os.File を要求している
    _, err := io.Copy(w, r)
    return err
}
```

### コンパイル時のインターフェース充足チェック

ある具象型が特定のインターフェースを満たすことを保証したい場合は、ブランク識別子への代入でコンパイル時に検証する。実行時まで気づかない実装漏れを防げる。

```go
// Good
type FileRepository struct{}

var _ Repository = (*FileRepository)(nil) // FileRepositoryがRepositoryを満たさなければコンパイルエラーになる

func (r *FileRepository) FindByID(ctx context.Context, id uint) (*Entity, error) {
    // ...
    return nil, nil
}
```

```go
// Bad
type FileRepository struct{}

func (r *FileRepository) FindById(ctx context.Context, id uint) (*Entity, error) { // メソッド名のtypoに気づけない（Repository.FindByIDを満たしていない）
    // ...
    return nil, nil
}
```

## 8. 構造体リテラル

構造体を生成するときはフィールド名を明示する。

```go
// Good
good := otherpkg.Type{A: 42}
```

```go
// Bad
r := csv.Reader{',', '#', 4, false, false, false, false}
```

複数行の構造体リテラルでは、括弧のインデントを揃える。

```go
// Good
good := []*Type{
    {Key: "multi"},
    {Key: "line"},
}
```

```go
// Bad
good := []*Type{
{Key: "multi"},
{Key: "line"},
}
```

## 9. 関数・メソッド設計

### 関数の長さとネストの深さ

1関数は60行以内に収める（`golangci-lint`の`funlen`リンターのデフォルト値に合わせ、CIで機械的に強制する）。ネストは`if`/`for`等で3段階までを目安とし、それ以上深くなる場合は早期return・ガード節、または別関数への抽出で浅くする。

```go
// Good
func ValidateTask(t *Task) error {
    if t == nil {
        return errors.New("task is nil")
    }

    if t.Name == "" {
        return errors.New("task name is required")
    }

    if t.DueDate.Before(time.Now()) {
        return errors.New("due date must be in the future")
    }

    return nil
}
```

```go
// Bad
func ValidateTask(t *Task) error {
    if t != nil {
        if t.Name != "" {
            if !t.DueDate.Before(time.Now()) {
                return nil
            } else {
                return errors.New("due date must be in the future")
            }
        } else {
            return errors.New("task name is required")
        }
    } else {
        return errors.New("task is nil")
    }
}
```

行数・ネスト段数の目安を超える場合は、ロジックのまとまりごとに別関数へ抽出することを優先し、コメントで区切っただけの1つの巨大な関数に留めない。

### 1行の文字数

厳密な文字数制限は設けない（`gofmt`は行の折り返しを行わないため、無理に改行するとかえって可読性が下がる）。ただし、1行が100文字を超える場合は、変数への切り出しや構造体化を検討する。CIで機械的に検出したい場合は、`golangci-lint`の`lll`リンターを`line-length: 100`で設定する。

```go
// Good
threshold := calculateThreshold(cfg.BaseRate, cfg.Multiplier)

if err := repo.UpdateStatus(ctx, taskID, threshold); err != nil {
    return fmt.Errorf("タスクの状態更新に失敗しました: %w", err)
}
```

```go
// Bad
if err := repo.UpdateStatus(ctx, taskID, calculateThreshold(cfg.BaseRate, cfg.Multiplier, cfg.Offset, cfg.RoundingMode)); err != nil {
    return fmt.Errorf("タスクの状態更新に失敗しました: %w", err)
}
```

### 関数の責務（単一責任）

1つの関数は1つのことだけを行う。入力の検証・業務ロジック・永続化・ログ出力・レスポンス整形など、性質の異なる処理を1つの関数に混在させない。

```go
// Good
func (uc *CreateTaskUseCase) Execute(ctx context.Context, cmd CreateTaskCommand) (*Task, error) {
    task, err := newTaskFromCommand(cmd)
    if err != nil {
        return nil, err
    }

    if err := uc.repo.Save(ctx, task); err != nil {
        return nil, err
    }

    return task, nil
}

func newTaskFromCommand(cmd CreateTaskCommand) (*Task, error) {
    // 入力からTaskを組み立てる処理のみ担当する
    // ...
    return &Task{}, nil
}
```

```go
// Bad
func (uc *CreateTaskUseCase) Execute(ctx context.Context, cmd CreateTaskCommand) (*Task, error) {
    // バリデーション・Entity組み立て・DB保存・ログ出力が
    // すべて1つの関数に詰め込まれている
    if cmd.Name == "" {
        return nil, errors.New("name is required")
    }

    task := &Task{Name: cmd.Name, CreatedAt: time.Now()}

    if err := uc.db.Create(task).Error; err != nil {
        log.Printf("failed to create task: %v", err)
        return nil, err
    }

    log.Printf("task created: %v", task.ID)

    return task, nil
}
```

### 入力検証とドメイン検証の責務分離

型・必須・フォーマットといったHTTPレベルの入力検証はPresentation層のRequest DTOで行い、状態遷移・整合性といった業務ルール検証はDomain（Domain Model採用時）またはstruct/関数（Active Record/Transaction Script採用時）で行う。同じ検証を両方の層で重複させない（アーキテクチャ規約「7. 横断的関心事の置き場所」に従う）。

```go
// Good

// Presentation: 型・必須のみ
type CreateTaskRequest struct {
    Name string `json:"name" binding:"required"`
}

// Domain: 業務ルール
func NewTask(name string, dueDate time.Time) (*Task, error) {
    if dueDate.Before(time.Now()) {
        return nil, errors.New("due date must be in the future")
    }

    return &Task{Name: name, DueDate: dueDate}, nil
}
```

```go
// Bad
type CreateTaskRequest struct {
    Name    string    `json:"name" binding:"required"`
    DueDate time.Time `json:"due_date" binding:"required"`
}

func (r CreateTaskRequest) Validate() error {
    // HTTPレベルの入力検証の中に業務ルール（締切は未来日であること）まで混在している
    if r.DueDate.Before(time.Now()) {
        return errors.New("due date must be in the future")
    }

    return nil
}
```

### レシーバー名

レシーバー名は短く、一貫した名前を使用する。

```go
type User struct {
    Name string
    Age  int
}
```

```go
// Good
func (u User) String() string {
    return fmt.Sprintf("%s (%d)", u.Name, u.Age)
}
```

```go
// Bad
func (user User) String() string {
    return fmt.Sprintf("%s (%d)", user.Name, user.Age)
}
```

### 値レシーバー

レシーバーを変更しない場合に使用する。

```go
// Good
func (u User) String() string {
    return fmt.Sprintf("%s (%d)", u.Name, u.Age)
}
```

```go
// Bad
func (u *User) String() string {
    return fmt.Sprintf("%s (%d)", u.Name, u.Age)
}
```

### ポインタレシーバー

レシーバーを変更する場合に使用する。

```go
// Good
func (u *User) UpdateAge(age int) {
    u.Age = age
}
```

```go
// Bad
func (u User) UpdateAge(age int) {
    u.Age = age
}
```

値レシーバーでは `u` のコピーを変更しているため、呼び出し元の `User` は変更されない。

### レシーバーの統一

同じ型のメソッドでは、基本的にポインタレシーバーか値レシーバーのどちらかに統一する。

```go
// Good
type User struct {
    Name string
    Age  int
}

func (u *User) UpdateAge(age int) {
    u.Age = age
}

func (u *User) String() string {
    return fmt.Sprintf("%s (%d)", u.Name, u.Age)
}
```

```go
// Bad
type User struct {
    Name string
    Age  int
}

func (u *User) UpdateAge(age int) {
    u.Age = age
}

func (u User) String() string {
    return fmt.Sprintf("%s (%d)", u.Name, u.Age)
}
```

### コピーしてはいけない型

`sync.Mutex` や `bytes.Buffer` など、コピーによって問題が発生する型はコピーしない。

```go
// Bad
mu := sync.Mutex{}
mu2 := mu
```

```go
// Good
mu := &sync.Mutex{}
```

コピーされて困るフィールドを持つ構造体も、基本的にポインタレシーバーを使用する。

```go
// Good
type Record struct {
    buf bytes.Buffer
}

func New() *Record {
    // ...
}

func (r *Record) Process(...) {
    // ...
}

func Consumer(r *Record) {
    // ...
}
```

```go
// Bad
type Record struct {
    buf bytes.Buffer
}

func Consumer(r Record) {
    // Record がコピーされる可能性がある
}
```

### 関数の引数

関数シグネチャは簡潔に保つ。

引数は目安として4つまでとする。それを超える場合は、構造体にまとめることを検討する。

```go
// Good
type CreateUserInput struct {
    Name     string
    Email    string
    Age      int
    Address  string
    IsActive bool
}

func CreateUser(input CreateUserInput) error {
    // ...
    return nil
}
```

```go
// Bad
func CreateUser(
    name string,
    email string,
    age int,
    address string,
    isActive bool,
) error {
    // ...
    return nil
}
```

### 名前付き戻り値

`naked return` を使用するためだけに名前付き戻り値を使用しない。

```go
// Bad
func (n *Node) Parent1() (node *Node)

func (n *Node) Parent2() (node *Node, err error)
```

```go
// Good
func (n *Node) Parent1() *Node

func (n *Node) Parent2() (*Node, error)
```

ただし、`defer` 内で戻り値を変更する必要がある場合は名前付き戻り値を使用してよい。

```go
// Good
func Process() (err error) {
    defer func() {
        if err != nil {
            err = fmt.Errorf("処理に失敗しました: %w", err)
        }
    }()

    err = doSomething()
    return
}
```

```go
// Bad
func Process() error {
    defer func() {
        // 名前付き戻り値がないため、ここで return 値を変更できない
    }()

    return doSomething()
}
```

### `defer` の使用

リソースの解放は確保した直後に `defer` で行い、ループ内で `defer` を使用しない。

```go
// Good
func ProcessFiles(paths []string) error {
    for _, path := range paths {
        if err := processFile(path); err != nil {
            return err
        }
    }

    return nil
}

func processFile(path string) error {
    f, err := os.Open(path)
    if err != nil {
        return err
    }
    defer f.Close()

    // f を使った処理
    return nil
}
```

```go
// Bad
func ProcessFiles(paths []string) error {
    for _, path := range paths {
        f, err := os.Open(path)
        if err != nil {
            return err
        }
        defer f.Close()

        // ループが終わるまでファイルディスクリプタが解放されない
    }

    return nil
}
```

`os.Exit` や `log.Fatal` を呼び出す可能性がある関数の中では、それより前に登録した `defer` が実行されない点に注意する。

## 10. `switch`

Go の `switch` は各 `case` の末尾で自動的に終了するため、通常の `break` は書かない。

```go
// Good
switch x {
case "A", "B":
    buf.WriteString(x)

case "C":
    // 別の箇所で処理される

default:
    return fmt.Errorf("未知の値です: %q", x)
}
```

```go
// Bad
switch x {
case "A", "B":
    buf.WriteString(x)
    break

case "C":
    break

default:
    return fmt.Errorf("未知の値です: %q", x)
}
```

### ループから抜ける場合

`for` ループから `switch` を抜けたい場合は、ラベル付き `break` を使用する。

```go
// Good
loop:
for {
    switch x {
    case "A":
        break loop
    }
}
```

```go
// Bad
for {
    switch x {
    case "A":
        break
    }
}
```

上記の `break` は `switch` だけを終了し、`for` ループ自体は終了しない。

### 型switch

`any`型の値の実際の型に応じて分岐する場合は、型アサーションの連鎖ではなく型switchを使用する。

```go
// Good
func describe(v any) string {
    switch v := v.(type) {
    case int:
        return fmt.Sprintf("int: %d", v)
    case string:
        return fmt.Sprintf("string: %q", v)
    case nil:
        return "nil"
    default:
        return fmt.Sprintf("unknown type: %T", v)
    }
}
```

```go
// Bad
func describe(v any) string {
    if i, ok := v.(int); ok {
        return fmt.Sprintf("int: %d", i)
    }
    if s, ok := v.(string); ok {
        return fmt.Sprintf("string: %q", s)
    }
    return "unknown"
}
```

型switchの`case nil`は、判定対象がインターフェース自体`nil`である場合のみ一致する。「12. `nil`の扱い」の「nilを保持するインターフェースはnilではない」のとおり、具象型のnilポインタを包んだインターフェースは`case nil`に一致せず、対応する具象型の`case`に一致する点に注意する。

## 11. スライス・配列・マップ

### 配列とスライスの使い分け

配列は要素数を型の一部として持つ固定長の値型で、代入・関数引数渡し時にコピーされる。ほとんどの場面ではスライスを使用し、配列は要素数が仕様として不変であるデータ（ハッシュ値等）に限定して使用する。

```go
// Good
func Sum(nums []int) int {
    total := 0
    for _, n := range nums {
        total += n
    }
    return total
}
```

```go
// Bad
func Sum(nums [10]int) int { // 要素数が10に固定され、呼び出し側の柔軟性を奪う
    total := 0
    for _, n := range nums {
        total += n
    }
    return total
}
```

```go
// Good（配列が適切な例）
type SHA256Hash [32]byte // ハッシュ値は仕様上常に32バイトであり、固定長が意味を持つ
```

### スライスのエイリアシング（`append`と裏側配列の共有）

スライスは裏側の配列への参照であり、複数のスライスが同じ配列を共有しうる。`append`は容量が足りる場合は既存の配列を書き換え、足りない場合のみ新しい配列を確保する。この挙動に依存したコードは、意図しない書き換えを引き起こす。

```go
// Bad
func addDefault(tasks []Task) []Task {
    return append(tasks, Task{Name: "default"})
}

original := make([]Task, 2, 3) // 容量が3あるため、addDefaultは新しい配列を確保しない
withDefault := addDefault(original)
// originalの裏側配列がwithDefaultの追加によって書き換えられる場合がある
```

```go
// Good
func addDefault(tasks []Task) []Task {
    result := make([]Task, len(tasks), len(tasks)+1)
    copy(result, tasks)
    return append(result, Task{Name: "default"}) // 明示的に新しい配列を確保してから追記する
}
```

呼び出し元のスライスを書き換えない関数を書く場合は、`append`を呼ぶ前に十分な独立した容量を確保するか、`copy`で複製してから操作する。

### マップの反復順序

`range`によるマップの反復順序は保証されず、実行のたびに変わる。出力やテストで決定的な順序が必要な場合は、キーを別途ソートしてから反復する。

```go
// Good
keys := make([]string, 0, len(m))
for k := range m {
    keys = append(keys, k)
}
sort.Strings(keys)

for _, k := range keys {
    fmt.Println(k, m[k])
}
```

```go
// Bad
for k, v := range m {
    fmt.Println(k, v) // 実行のたびに出力順序が変わる
}
```

## 12. `nil` の扱い

nil スライスと空スライスは意味的に区別できるが、多くの操作では同じように扱える。`len()` や `range` は nil スライスに対しても安全に動作する。

```go
// Good
var users []User // nil スライス。len(users) == 0

for _, u := range users {
    // nil スライスに対しても安全にループできる
}
```

nil マップへの書き込みは panic するため、書き込みが必要な場合は `make` で初期化する。

```go
// Good
counts := make(map[string]int)
counts["a"]++
```

```go
// Bad
var counts map[string]int
counts["a"]++ // panic: assignment to entry in nil map
```

nil マップからの読み取りはゼロ値を返すため安全だが、書き込みの可能性がある場合は必ず初期化する。

### nil ポインタレシーバー

ポインタレシーバーを持つメソッドは、レシーバーが nil でも呼び出せる場合がある。レシーバーが nil であることを許容する設計にする場合は、メソッド内で明示的にチェックする。

```go
// Good
func (u *User) Name() string {
    if u == nil {
        return ""
    }

    return u.name
}
```

```go
// Bad
func (u *User) Name() string {
    // u が nil の場合に panic する
    return u.name
}
```

### nilを保持するインターフェースはnilではない

具象型の nil ポインタを `error` 等のインターフェースへ代入すると、インターフェース自体は nil にならない（型情報が残るため）。`error` を返す関数で、具象型のポインタ変数をそのまま返すと、呼び出し側の `err != nil` 判定が意図せず true になる。

```go
// Bad
type MyError struct{}

func (e *MyError) Error() string { return "my error" }

func doSomething() error {
    var err *MyError // nil

    if false { // 実際にはエラーが発生しなかった
        err = &MyError{}
    }

    return err // *MyError型のnilがerrorインターフェースに包まれ、err != nilになる
}

func caller() {
    if err := doSomething(); err != nil {
        // errは実際にはnilの*MyErrorだが、ここを通ってしまう
    }
}
```

```go
// Good
func doSomething() error {
    var err *MyError

    if false {
        err = &MyError{}
    }

    if err == nil {
        return nil // 具象型のポインタではなく、明示的にnilのerrorを返す
    }

    return err
}
```

具象型のエラー変数をそのまま `error` として返さず、`nil`かどうかを明示的に判定してから返す。

## 13. Generics（型パラメータ）

型に依存しない汎用的な処理で、複数の型に対して同じロジックを重複実装している場合に型パラメータを使用する。

```go
// Good
func Map[T, U any](s []T, f func(T) U) []U {
    result := make([]U, 0, len(s))

    for _, v := range s {
        result = append(result, f(v))
    }

    return result
}
```

```go
// Bad
func MapUsersToNames(users []User) []string {
    names := make([]string, 0, len(users))
    for _, u := range users {
        names = append(names, u.Name)
    }
    return names
}

func MapTasksToIDs(tasks []Task) []string {
    ids := make([]string, 0, len(tasks))
    for _, t := range tasks {
        ids = append(ids, t.ID)
    }
    return ids
}
```

型パラメータには単一の大文字を基本とし、意味が分かりにくい場合のみ短い単語にする。

```go
// Good
func Map[T, U any](s []T, f func(T) U) []U { /* ... */ }
```

```go
// Bad
func Map[InputType, OutputType any](s []InputType, f func(InputType) OutputType) []OutputType { /* ... */ }
```

単一の具象型でしか使わない場合や `any` 一つで表現できる場合は Generics を使用しない。

```go
// Bad
// 実際には string にしか使わないのに型パラメータ化している
func Identity[T any](v T) T {
    return v
}
```

### `any` 以外の制約

型パラメータに対して比較・演算等の操作が必要な場合は、`any`ではなく操作を許容する制約を使用する。マップのキーに使う、`==`で比較する等の場合は`comparable`を使用する。

```go
// Good
func Contains[T comparable](s []T, target T) bool {
    for _, v := range s {
        if v == target { // comparable制約により == が使える
            return true
        }
    }
    return false
}
```

```go
// Bad
func Contains[T any](s []T, target T) bool {
    for _, v := range s {
        if v == target { // any制約では == が使えずコンパイルエラーになる
            return true
        }
    }
    return false
}
```

数値型に対して四則演算が必要な場合は、`golang.org/x/exp/constraints`相当のインターフェースを自前で定義するか、標準ライブラリの`cmp.Ordered`（大小比較のみでよい場合）を使用する。

```go
// Good
func Max[T cmp.Ordered](a, b T) T {
    if a > b {
        return a
    }
    return b
}
```

## 14. `any`

Go 1.18 以降では `interface{}` の代わりに `any` を使用する。

```go
// Good
func Process(data any) error {
    // ...
    return nil
}
```

```go
// Bad
func Process(data interface{}) error {
    // ...
    return nil
}
```

`any`型の値から具体的な型を取り出す際は、型が確実に一致すると分かっている場合を除き、comma-ok形式の型アサーションを使用する。単一の戻り値形式は、型が一致しない場合にpanicする。

```go
// Good
func Process(data any) error {
    s, ok := data.(string)
    if !ok {
        return fmt.Errorf("unexpected type: %T", data)
    }

    // sを使った処理
    return nil
}
```

```go
// Bad
func Process(data any) error {
    s := data.(string) // dataがstringでない場合にpanicする
    // ...
    return nil
}
```

## 15. 変数のシャドーイング

内側のスコープで`:=`を使うと、同名の外側変数を意図せず隠す（シャドーイングする）ことがある。特に`if`/`for`の条件節や、ネストしたブロック内でのエラー変数の再宣言で発生しやすい。

```go
// Bad
func process() error {
    var err error

    if x, err := doSomething(); err != nil { // このerrはifブロック内だけのローカル変数
        return err
    } else {
        _ = x
    }

    return err // 常にnilが返る（外側のerrは更新されていない）
}
```

```go
// Good
func process() error {
    var err error

    x, err := doSomething() // 外側のerrに代入する（新規宣言しない）
    if err != nil {
        return err
    }

    _ = x
    return err
}
```

`golangci-lint`の`govet`（`shadow`チェック）を有効にすると、この種のシャドーイングを機械的に検出できる。既存の変数へ代入する意図がある場合は、ブロックをまたいで新しい`:=`を使わず、`=`で代入する。

## 16. 構造体タグ

`json` タグは省略せず明示し、命名は `camelCase` に統一する。

```go
// Good
type CreateUserRequest struct {
    Name  string `json:"name"`
    Email string `json:"email"`
}
```

```go
// Bad
type CreateUserRequest struct {
    Name  string // タグがなく、フィールド名がそのまま公開される
    Email string `json:"Email"` // PascalCase になっている
}
```

入力値検証には Request DTO 側でバリデーションタグを使用し、ドメインルールの検証と役割を分ける。

```go
// Good
type CreateUserRequest struct {
    Name  string `json:"name" binding:"required"`
    Email string `json:"email" binding:"required,email"`
}
```

### `omitempty` とゼロ値の扱い

`omitempty`は、フィールドがゼロ値（数値の`0`・空文字列・`false`・空スライス等）の場合にJSON出力から除外する。「値が未設定であること」と「値が意図的にゼロ値であること」を区別する必要があるレスポンスには使用しない。

```go
// Bad
type TaskResponse struct {
    Priority int `json:"priority,omitempty"` // Priorityが0（最優先）の場合、フィールド自体が消えてしまう
}
```

区別が必要な場合はポインタ型にする。

```go
// Good
type TaskResponse struct {
    Priority *int `json:"priority,omitempty"` // 未設定はnil、0は明示的な値として区別できる
}
```

`bool`のfalseや空スライスについても同様に、「未指定」と「明示的にfalse/空」を区別する必要があるフィールドには`omitempty`を付けない。

## 17. `time.Time` とタイムゾーン

内部で保持・保存する時刻は UTC に統一し、表示・入出力時にのみ必要なタイムゾーンへ変換する。

```go
// Good
func CreateTask(name string) *Task {
    return &Task{
        Name:      name,
        CreatedAt: time.Now().UTC(),
    }
}
```

```go
// Bad
func CreateTask(name string) *Task {
    jst, _ := time.LoadLocation("Asia/Tokyo")

    return &Task{
        Name:      name,
        CreatedAt: time.Now().In(jst), // 保存時点でローカルタイムゾーンに依存する
    }
}
```

表示用に変換する場合は、Presentation 層など出力に近い箇所でのみ行う。

```go
// Good
func (r Response) FormatCreatedAt() string {
    jst, _ := time.LoadLocation("Asia/Tokyo")
    return r.CreatedAt.In(jst).Format("2006-01-02 15:04:05")
}
```

### 時刻の比較

`time.Time`の同一時刻判定には`==`を使用しない。`time.Time`はタイムゾーン情報等の内部状態を含む構造体であり、同じ瞬間を表していても内部表現が異なれば`==`は`false`になりうる。

```go
// Good
func isSameTime(a, b time.Time) bool {
    return a.Equal(b)
}
```

```go
// Bad
func isSameTime(a, b time.Time) bool {
    return a == b // UTC変換済みかどうか等の内部状態の違いで、同じ瞬間でもfalseになりうる
}
```

`time.Time`をマップのキーにする、`cmp.Diff`で比較する等の場合も同様の理由で意図しない不一致が起こりうるため、比較前に`UTC()`等で正規化するか、専用の比較ロジックを使用する。

## 18. エラーハンドリング

Go ではエラーを明示的に処理する。

### エラーを無視しない

基本的に、関数はエラーを追加の戻り値として返す。

```go
// Good
value, ok := Lookup(key)
if !ok {
    return fmt.Errorf("キー %q の値が見つかりません", key)
}

return Parse(value)
```

```go
// Bad
value, _ := Lookup(key)

return Parse(value)
```

### エラーは最後の戻り値にする

```go
// Good
func ParseUser(data []byte) (User, error) {
    var u User

    err := json.Unmarshal(data, &u)

    return u, err
}
```

```go
// Bad
func ParseUser(data []byte) (error, User) {
    var u User

    err := json.Unmarshal(data, &u)

    return err, u
}
```

### エラーのラップ

エラーを追加情報とともに返す場合は `fmt.Errorf` と `%w` を使用する。

```go
// Good
func ReadConfig(filename string) (*Config, error) {
    data, err := os.ReadFile(filename)
    if err != nil {
        return nil, fmt.Errorf("設定ファイルの読み込みに失敗しました: %w", err)
    }

    var config Config
    if err := json.Unmarshal(data, &config); err != nil {
        return nil, fmt.Errorf("設定ファイルの解析に失敗しました: %w", err)
    }

    return &config, nil
}
```

```go
// Bad
func ReadConfig(filename string) (*Config, error) {
    data, err := os.ReadFile(filename)
    if err != nil {
        return nil, fmt.Errorf("設定ファイルの読み込みに失敗しました: %v", err)
    }

    var config Config
    if err := json.Unmarshal(data, &config); err != nil {
        return nil, fmt.Errorf("設定ファイルの解析に失敗しました: %v", err)
    }

    return &config, nil
}
```

`%v` では元のエラーとのラップ関係が維持されないため、エラーをラップする場合は `%w` を使用する。

### エラー値の定義と `errors.Is` / `errors.As`

呼び出し元がエラーの種類を判定できるようにする場合は、sentinel error またはエラー型として定義し、比較には `==` や文字列比較ではなく `errors.Is` / `errors.As` を使用する。

```go
// Good
var ErrNotFound = errors.New("not found")

func FindUser(id string) (*User, error) {
    // ...
    return nil, fmt.Errorf("ユーザー %q の取得に失敗しました: %w", id, ErrNotFound)
}

if errors.Is(err, ErrNotFound) {
    // ...
}
```

Presentation層でエラーをHTTPレスポンス・ログへ変換する際の判定方法（`errors.As`によるAppErrorの一括判定）は、アーキテクチャ規約「12. Error変換パターン（AppError）」に従う。

```go
// Bad
func FindUser(id string) (*User, error) {
    // ...
    return nil, errors.New("not found")
}

if err.Error() == "not found" {
    // 文字列比較ではラップされたエラーを判定できない
}
```

フィールドを持つ独自エラー型を判定したい場合は `errors.As` を使用する。

```go
// Good
type ValidationError struct {
    Field string
}

func (e *ValidationError) Error() string {
    return fmt.Sprintf("invalid field: %s", e.Field)
}

var verr *ValidationError
if errors.As(err, &verr) {
    // verr.Field を使用できる
}
```

### 複数回ラップされたエラーの判定

`errors.Is` / `errors.As` は`Unwrap()`チェーンを辿るため、エラーが複数の層で`%w`によりラップされていても、途中の層を気にせず判定できる。呼び出し元は、エラーが何回・どの層でラップされたかを意識する必要はない。

```go
// Good
var ErrNotFound = errors.New("not found")

func repositoryFind() error {
    return ErrNotFound
}

func usecaseExecute() error {
    if err := repositoryFind(); err != nil {
        return fmt.Errorf("ユースケースの実行に失敗しました: %w", err)
    }
    return nil
}

func handlerCall() error {
    if err := usecaseExecute(); err != nil {
        return fmt.Errorf("ハンドラでの処理に失敗しました: %w", err)
    }
    return nil
}

// 2回ラップされていても判定できる
err := handlerCall()
if errors.Is(err, ErrNotFound) {
    // ...
}
```

```go
// Bad
err := handlerCall()

// 文字列に埋め込まれたラップ済みメッセージを直接比較しようとする
if err.Error() == "ハンドラでの処理に失敗しました: ユースケースの実行に失敗しました: not found" {
    // ラップ時のメッセージ文言を1文字でも変更すると判定が壊れる
}
```

`fmt.Errorf`で`%w`を使わず`%v`でラップした場合は、このチェーンが途切れ`errors.Is`が`false`を返す点に注意する（「エラーのラップ」節参照）。

### エラー処理を先に行う

エラー処理後は早期 `return` し、正常系を `else` の中に入れない。

```go
// Good
x, err := f()
if err != nil {
    // エラー処理
    return
}

// x を使う処理
```

```go
// Bad
if x, err := f(); err != nil {
    // エラー処理
    return
} else {
    // x を使う処理
}
```

### In-band error を避ける

`-1`、`null`、空文字列などの特殊な値をエラーとして利用しない。

```go
// Bad
func Lookup(key string) int
```

代わりに複数戻り値を使用する。

```go
// Good
func Lookup(key string) (value string, ok bool)
```

### 複数のエラーをまとめる

バリデーション等、複数箇所で発生したエラーを1つにまとめて返す必要がある場合は`errors.Join`を使用する。まとめられたエラーに対しても`errors.Is` / `errors.As`は個々の内包エラーを判定できる。

```go
// Good
func ValidateTask(t *Task) error {
    var errs []error

    if t.Name == "" {
        errs = append(errs, errors.New("name is required"))
    }

    if t.DueDate.Before(time.Now()) {
        errs = append(errs, ErrDueDateInPast)
    }

    return errors.Join(errs...) // errsが空ならnilを返す
}

// 呼び出し側
if err := ValidateTask(t); err != nil {
    if errors.Is(err, ErrDueDateInPast) {
        // 複数エラーがまとまっていても個別に判定できる
    }
}
```

```go
// Bad
func ValidateTask(t *Task) error {
    var messages []string

    if t.Name == "" {
        messages = append(messages, "name is required")
    }

    if t.DueDate.Before(time.Now()) {
        messages = append(messages, "due date must be in the future")
    }

    if len(messages) == 0 {
        return nil
    }

    return errors.New(strings.Join(messages, "; ")) // 文字列結合では個々のエラーをerrors.Isで判定できない
}
```

## 19. `panic` の扱い

通常の処理では `panic()` を使用しない。

エラーを返せる場合は `return err` を使用する。

```go
// Good
func Process() error {
    if err := doSomething(); err != nil {
        return err
    }

    return nil
}
```

```go
// Bad
func Process() error {
    if err := doSomething(); err != nil {
        panic(err)
    }

    return nil
}
```

### `Must` パターン

プログラム起動時など、失敗したらプログラム自体を終了させるべきセットアップ処理では `Must` パターンを使用できる。

```go
// Good
func MustParse(version string) *Version {
    v, err := Parse(version)
    if err != nil {
        log.Fatalf("MustParse(%q) = _, %v", version, err)
    }

    return v
}
```

```go
// Bad
func ValidateUserInput(version string) *Version {
    v, err := Parse(version)
    if err != nil {
        log.Fatalf("入力値の解析に失敗しました: %v", err)
    }

    return v
}
```

`Must` 関数はユーザー入力のバリデーションなどには使用せず、プログラム起動時の前提条件などに限定する。

## 20. `context.Context`

`context.Context` は API 境界やプロセス間で、以下の情報を伝搬するために使用する。

* キャンセル
* デッドライン
* 認証情報
* トレース情報

### 関数の第1引数にする

関数シグネチャでは原則として第1引数に置く。

```go
// Good
func F(ctx context.Context, otherArg string) error {
    // ...
    return nil
}
```

```go
// Bad
func F(otherArg string, ctx context.Context) error {
    // ...
    return nil
}
```

### HTTP ハンドラ

HTTP ハンドラでは `req.Context()` を使用する。

```go
// Good
func Handler(w http.ResponseWriter, req *http.Request) {
    ctx := req.Context()

    // ctx を使用する
}
```

```go
// Bad
func Handler(w http.ResponseWriter, req *http.Request) {
    ctx := context.Background()

    // HTTP リクエストの context を使用していない
    _ = ctx
}
```

### エントリーポイント

エントリーポイント関数では `context.Background()` を使用する。

```go
// Good
func main() {
    ctx := context.Background()

    // ...
    _ = ctx
}
```

```go
// Bad
func main() {
    ctx := context.TODO()

    // ...
    _ = ctx
}
```

### テスト

Go 1.24 以降のテストでは `t.Context()` を使用できる。

```go
// Good
func TestSomething(t *testing.T) {
    ctx := t.Context()

    // ...
    _ = ctx
}
```

```go
// Bad
func TestSomething(t *testing.T) {
    ctx := context.Background()

    // テスト専用の context を利用せず Background を直接使用している
    _ = ctx
}
```

### 構造体のフィールドに持たせない

`context.Context` を構造体のフィールドとして保持しない。

```go
// Good
type Server struct {
    // ...
}

func (s *Server) Process(ctx context.Context, req *Request) error {
    // ...
    return nil
}
```

```go
// Bad
type Server struct {
    ctx context.Context
}
```

独自の Context 型は作成せず、`context.Context` を使用する。

```go
// Good
func Process(ctx context.Context) error {
    // ...
    return nil
}
```

```go
// Bad
type RequestContext struct {
    // 独自の Context 型を作成している
}

func Process(ctx *RequestContext) error {
    // ...
    return nil
}
```

### `context.WithValue` の使用基準

`context.WithValue`で運んでよいのは、リクエストスコープの横断的関心事（アーキテクチャ規約「7. 横断的関心事の置き場所」）に限る。current user・トレースID・ロケール等が該当する。Command/DTO/Entityといった業務データを運ぶ手段としては使用せず、関数の引数として明示的に渡す。

```go
// Good
type ctxKeyCurrentUser struct{}

func WithCurrentUser(ctx context.Context, u *CurrentUser) context.Context {
    return context.WithValue(ctx, ctxKeyCurrentUser{}, u)
}

func CurrentUserFromContext(ctx context.Context) (*CurrentUser, bool) {
    u, ok := ctx.Value(ctxKeyCurrentUser{}).(*CurrentUser)
    return u, ok
}
```

```go
// Bad
ctx = context.WithValue(ctx, "user", u) // 文字列キーは他パッケージのキーと衝突しうる
```

```go
// Bad
ctx = context.WithValue(ctx, "cmd", createTaskCommand) // 業務データをcontext経由で渡している
```

キーには非公開の空struct型（`type ctxKeyCurrentUser struct{}`）を使用し、文字列や公開された型を使わない。同じパッケージ内でキーの衝突を避けるため、値の設定・取得を行う関数（`WithXxx` / `XxxFromContext`）をキーの型と同じ場所にまとめて定義する。

## 21. 並行プログラミング

`goroutine` を使用する場合は、ライフサイクルと終了条件を明確にする。

```go
func processData(ctx context.Context, data <-chan string) <-chan Result {
    results := make(chan Result)

    go func() {
        defer close(results)

        for {
            select {
            case item := <-data:
                if item == "" {
                    return
                }

                results <- process(item)

            case <-ctx.Done():
                return
            }
        }
    }()

    return results
}
```

```go
// Bad
func processData(data <-chan string) <-chan Result {
    results := make(chan Result)

    go func() {
        for item := range data {
            results <- process(item)
        }
    }()

    return results
}
```

上記のように終了条件やキャンセル処理が明確でない `goroutine` は、リークにつながる可能性がある。

`goroutine` のリークやデータ競合を避けるため、`goroutine` がいつ終了するのかを明確にする。

### 同期処理を優先する

可能な場合は、非同期関数より同期関数を優先する。

```go
// Good
func Lookup(key string) (Value, error) {
    // キーに対応する値を直接返す
}
```

```go
// Bad
func LookupAsync(key string) <-chan Value {
    result := make(chan Value)

    go func() {
        result <- lookup(key)
    }()

    return result
}
```

並行処理は、必要になった側で追加できるようにする。

### 通信による共有

前項のとおり並行処理は必要な場合にのみ導入するが、複数のgoroutineが同じデータをやり取りする必要がある場合は、共有メモリを`sync.Mutex`等でロックするより、チャンネルを介してデータの所有権を受け渡す設計を優先する（Go言語の "Do not communicate by sharing memory; instead, share memory by communicating." という設計思想に基づく）。

```go
// Good
func worker(jobs <-chan Job, results chan<- Result) {
    for job := range jobs {
        results <- process(job) // 所有権をチャンネル経由で受け渡す
    }
}
```

```go
// Bad
var (
    mu      sync.Mutex
    results []Result
)

func worker(jobs <-chan Job) {
    for job := range jobs {
        r := process(job)

        mu.Lock()
        results = append(results, r) // 共有変数をロックで保護する設計
        mu.Unlock()
    }
}
```

### 非ブロッキングなチャネル操作

チャネルへの送受信で相手の準備を待たずに処理を続けたい場合は、`select`に`default`を組み合わせる。`default`のない`select`は、いずれかのcaseが可能になるまでブロックする。

```go
// Good
select {
case results <- r:
    // 送信できた
default:
    // バッファが埋まっている等の理由で送信できない場合はスキップする
}
```

```go
// Bad
results <- r // バッファ付きチャネルが埋まっていると、受信側が処理するまでブロックし続ける
```

`ctx.Done()`と組み合わせて、キャンセルを見ながら非ブロッキングに送受信する場合も同様に`select`を使う（「21. 並行プログラミング」冒頭の`processData`例を参照）。

### goroutine内でのpanicとrecover

goroutine内で発生した`panic`は、そのgoroutine内で`recover`しない限り、呼び出し元では捕捉できずプロセス全体をクラッシュさせる。1件の処理の失敗でプロセス全体を落としてはならない箇所（アーキテクチャ規約「13. 非同期ジョブ実行パターン（JobQueue）」のワーカー等）では、goroutineの先頭で`defer`と`recover`を用いて保護する。

```go
// Good
func (w *Worker) runJob(job Job) {
    defer func() {
        if r := recover(); r != nil {
            w.logger.Error("job panicked", "job_type", job.Type, "recovered", r)
            // このジョブの失敗として扱い、プロセス全体は継続する
        }
    }()

    w.handlers[job.Type](job)
}
```

```go
// Bad
func (w *Worker) runJob(job Job) {
    w.handlers[job.Type](job) // 1件のジョブがpanicすると、ワーカーgoroutine、あるいはmainまで巻き込んでプロセス全体が終了する
}
```

`recover`は、goroutineの不具合を隠蔽する目的で乱用しない（「19. `panic`の扱い」のとおり、通常の処理では`panic`自体を使わない）。あくまで、他の処理から独立して動くgoroutine（ワーカー・リクエストごとのgoroutine等）の境界を保護する用途に限定する。

## 22. ロギング

不要なフォーマット指定は避ける。

```go
// Good
log.Info(value)
```

```go
// Bad
log.Infof("%v", value)
```

フォーマットが必要な場合は、フォーマット用のメソッドを使用する。

```go
// Good
log.Infof("ユーザー ID: %d", userID)
```

```go
// Bad
log.Info(fmt.Sprintf("ユーザー ID: %d", userID))
```

### 構造化ロギング

ログはメッセージと key-value のペアを分離した構造化ログとして出力し、文字列連結で組み立てない。

```go
// Good
logger.InfoContext(ctx, "user created", "user_id", userID, "email", email)
```

```go
// Bad
logger.Info(fmt.Sprintf("user created: user_id=%s email=%s", userID, email))
```

本番環境では`slog.JSONHandler`、開発環境では`slog.TextHandler`を、設定値に応じて切り替える。

`context.Context` を伝搬させ、リクエスト単位でトレース情報などを付与できるようにする。

```go
// Good
func (h *Handler) CreateUser(w http.ResponseWriter, req *http.Request) {
    ctx := req.Context()

    if err := h.usecase.Execute(ctx, input); err != nil {
        h.logger.ErrorContext(ctx, "failed to create user", "error", err)
        // ...
    }
}
```

```go
// Bad
func (h *Handler) CreateUser(w http.ResponseWriter, req *http.Request) {
    if err := h.usecase.Execute(context.Background(), input); err != nil {
        log.Println("failed to create user:", err)
    }
}
```

### ログレベルの使い分け

|レベル|用途|
|-|-|
|`Debug`|開発時の詳細な追跡情報。本番環境では通常無効にする|
|`Info`|正常な業務イベント（作成・更新・ログイン成功等）の記録|
|`Warn`|異常だが処理継続可能な状態（リトライ発生、非推奨APIの利用等）|
|`Error`|処理を継続できない失敗。呼び出し元へのエラー返却を伴う|
|`Fatal`|プログラムが続行不能で終了する場合のみ使用する。HTTPハンドラ内では使用しない|

```go
// Good
logger.DebugContext(ctx, "query built", "sql", query, "args", args)
logger.InfoContext(ctx, "task created", "task_id", task.ID)
logger.WarnContext(ctx, "retrying external API call", "attempt", attempt)
logger.ErrorContext(ctx, "failed to save task", "error", err)

// Fatalはエントリーポイントの起動失敗等、プロセスを止めるべき場面に限定する
func main() {
    db, err := connectDB(cfg)
    if err != nil {
        logger.Error("failed to connect to database", "error", err)
        os.Exit(1) // log.Fatal相当だが、slog経由で構造化したい場合はこの形にする
    }
}
```

```go
// Bad
logger.ErrorContext(ctx, "task created", "task_id", task.ID) // 正常イベントをErrorで記録している
logger.InfoContext(ctx, "failed to save task", "error", err) // 失敗をInfoで記録し、アラート対象から漏れる
```

### 同じエラーを複数層でログしない

1つのエラーは、それを最終的に処理する層（原則としてPresentation層。リトライ等の対応を行う場合はその層）で1回だけログする。エラーを`return`する箇所すべてでログを出す多重ログは避ける。

```go
// Good
func (uc *CreateTaskUseCase) Execute(ctx context.Context, cmd CreateTaskCommand) (*Task, error) {
    task, err := uc.repo.Save(ctx, cmd)
    if err != nil {
        return nil, fmt.Errorf("タスクの保存に失敗しました: %w", err) // ログはしない
    }

    return task, nil
}

func (h *Handler) CreateTask(w http.ResponseWriter, req *http.Request) {
    if _, err := h.usecase.Execute(req.Context(), cmd); err != nil {
        h.reportError(req, err) // ログ出力・レスポンス整形は1箇所の共通処理に委譲する
        return
    }
    // ...
}
```

`reportError`相当の処理は、Handlerごとに個別実装せず1箇所（本プロジェクトの場合、Ginの集中エラーハンドリングミドルウェア）にまとめる。エラー種別の判定（`errors.As`によるAppErrorの一括判定）とログレベルの決定方法はアーキテクチャ規約「12. Error変換パターン（AppError）」、Ginでの具体的な実装はGin規約「8. エラーハンドリングミドルウェア」を参照。

```go
// Bad
func (uc *CreateTaskUseCase) Execute(ctx context.Context, cmd CreateTaskCommand) (*Task, error) {
    task, err := uc.repo.Save(ctx, cmd)
    if err != nil {
        log.Printf("failed to save task: %v", err) // ここでもログ
        return nil, err
    }

    return task, nil
}

func (h *Handler) CreateTask(w http.ResponseWriter, req *http.Request) {
    if _, err := h.usecase.Execute(req.Context(), cmd); err != nil {
        log.Printf("failed to create task: %v", err) // 同じエラーを再度ログ（多重ログ）
    }
}
```

### ログに含めてはいけない情報

パスワード・トークン・認証情報・個人を特定できる情報（氏名・メールアドレス・電話番号等）を、平文のままログに出力しない。識別が必要な場合はIDのみを出力する。

```go
// Good
logger.InfoContext(ctx, "user login succeeded", "user_id", userID)
```

```go
// Bad
logger.InfoContext(ctx, "user login succeeded", "email", email, "password", password)
```

## 26. テスト

```text

```

```text

```

### テスト命名

テスト関数は `Test` に続けて対象の型・関数・メソッドなどを表す名前にする。

```go
// Good

    // ...

```

```go
// Bad
```

### テーブル駆動テスト

同じロジックで複数のケースをテストする場合は、テーブル駆動テストを使用する。

```go
// Good
func TestCompare(t *testing.T) {
    compareTests := []struct {
        a, b string
        want int
    }{
        {"", "", 0},
        {"a", "", 1},
        {"", "a", -1},
        {"abc", "abc", 0},
    }

    for _, test := range compareTests {
        got := Compare(test.a, test.b)

        if got != test.want {
            t.Errorf(
                "Compare(%q, %q) = %v, want %v",
                test.a,
                test.b,
                got,
                test.want,
            )
        }
    }
}
```

```go
// Bad
func TestCompare(t *testing.T) {
    if Compare("", "") != 0 {
        t.Error("空文字列同士の比較に失敗しました")
    }

    if Compare("a", "") != 1 {
        t.Error("a と空文字列の比較に失敗しました")
    }

    if Compare("", "a") != -1 {
        t.Error("空文字列と a の比較に失敗しました")
    }

    if Compare("abc", "abc") != 0 {
        t.Error("abc 同士の比較に失敗しました")
    }
}
```

正常系の戻り値だけでなく、エラーケースもテーブルに含める場合は、期待するエラー（またはエラーの有無）をフィールドとして持たせる。

```go
// Good
func TestParseUser(t *testing.T) {
    tests := []struct {
        name    string
        input   []byte
        wantErr error // 期待するエラー。nilなら成功を期待する
    }{
        {name: "valid", input: []byte(`{"name":"taro"}`), wantErr: nil},
        {name: "empty name", input: []byte(`{"name":""}`), wantErr: ErrNameRequired},
        {name: "malformed json", input: []byte(`{`), wantErr: ErrInvalidFormat},
    }

    for _, tt := range tests {
        t.Run(tt.name, func(t *testing.T) {
            _, err := ParseUser(tt.input)

            if tt.wantErr == nil {
                if err != nil {
                    t.Fatalf("ParseUser() error = %v, want nil", err)
                }
                return
            }

            if !errors.Is(err, tt.wantErr) {
                t.Fatalf("ParseUser() error = %v, want %v", err, tt.wantErr)
            }
        })
    }
}
```

```go
// Bad
func TestParseUser(t *testing.T) {
    tests := []struct {
        name    string
        input   []byte
        wantErr bool // エラーの有無しか区別できず、どのエラーかを検証できない
    }{
        {name: "valid", input: []byte(`{"name":"taro"}`), wantErr: false},
        {name: "empty name", input: []byte(`{"name":""}`), wantErr: true},
    }

    for _, tt := range tests {
        t.Run(tt.name, func(t *testing.T) {
            _, err := ParseUser(tt.input)
            if (err != nil) != tt.wantErr {
                t.Fatalf("ParseUser() error = %v, wantErr %v", err, tt.wantErr)
            }
        })
    }
}
```

### テストケース名

テストケースには意味のある名前を付ける。

```go
// Good
for _, d := range data {
    t.Run(d.name, func(t *testing.T) {
        got := Translate(d.srcLang, d.dstLang, d.srcText)

        if got != d.wantDstText {
            t.Errorf(
                "%s\nTranslate(%q, %q, %q) = %q, want %q",
                d.desc,
                d.srcLang,
                d.dstLang,
                d.srcText,
                got,
                d.wantDstText,
            )
        }
    })
}
```

```go
// Bad
for i, d := range data {
    t.Run(fmt.Sprintf("%d", i), func(t *testing.T) {

```

テストケースのインデックスをテスト名として使用しない。

### サブテスト

サブテストは、他のテストケースの実行結果や初期状態に依存させない。

```go

    t.Run(test.name, func(t *testing.T) {
        // 各テストケースで独立した状態を使用する

}
```

```go
// Bad

for _, test := range tests {
```

### テストカバレッジ方針

以下を必須のテスト対象とする。

* Domain（Domain Model採用時）・struct（Active Record採用時）のメソッドが持つ業務ルール・状態遷移
* UseCase / 関数（Transaction Script採用時）の正常系・主要な異常系
* Repository/Store実装（Domain Model/Active Record共通）

以下は、業務ロジックを含まない場合に限りテストを必須としない。

* 単純なGetter/Setterのみのメソッド
* フレームワークへの委譲のみを行うHandler（フレームワーク自体のテストで担保される範囲）

Presentation層のHandlerは、Request/Responseの変換とUseCase呼び出しの結線を確認する範囲に限定し、業務ロジックの網羅はUseCase/Domain側のテストで担保する。

```go
// Good
// UseCase側で業務ルールを網羅的にテストする
func TestCreateTaskUseCase_Execute(t *testing.T) {
    tests := []struct {
        name    string
        input   CreateTaskCommand
        wantErr error
    }{

        {name: "名前が空だとエラー", input: CreateTaskCommand{Name: ""}, wantErr: ErrNameRequired},
        {name: "期限が過去だとエラー", input: CreateTaskCommand{Name: "task", DueDate: past}, wantErr: ErrDueDateInPast},
    }
    // ...業務ルールのケースを網羅する
}

// Handler側は結線のみを確認する（正常系1件・バインドエラー1件で十分）
func TestTaskHandler_CreateTask(t *testing.T) {
    tests := []struct {
        name       string
        body       string
        wantStatus int
    }{
        {name: "正常なリクエストは201を返す", body: `{"name":"task"}`, wantStatus: http.StatusCreated},
        {name: "不正なJSONは422を返す", body: `{`, wantStatus: http.StatusUnprocessableEntity},
    }
    // ...業務ルールの全パターンはここでは繰り返さない
}
```

```go
// Bad
// Handler側のテストで業務ルールのバリエーションまで網羅しようとする
func TestTaskHandler_CreateTask(t *testing.T) {
    tests := []struct {

        {name: "期限が今日", body: `{"name":"task","due_date":"today"}`, wantStatus: 422},
        // UseCase側のテストと重複し、Handlerテストが肥大化する
    }
}
```

### slice の容量を事前確保

必要なサイズが事前に分かる場合は、容量を指定して確保する。

```go
// Good
func processItems(items []string) []Result {
    results := make([]Result, 0, len(items))

    for _, item := range items {
        results = append(results, process(item))
    }

}
```

```go
// Bad
func processItems(items []string) []Result {
    var results []Result

    for _, item := range items {
        results = append(results, process(item))
    }

    return results
}
```

### `strings.Builder`

文字列を大量に連結する場合は `strings.Builder` を使用する。

```go
// Good
func buildMessage(parts []string) string {
    var builder strings.Builder

    builder.Grow(estimateSize(parts))

    for _, part := range parts {
        builder.WriteString(part)
    }

    return builder.String()
}
```

```go
// Bad
func buildMessage(parts []string) string {
    var message string

    for _, part := range parts {
        message += part
    }

    return message
}
```

```go
// Bad
// ボトルネックを調査せず、推測だけでコードを複雑化する。
```

## 28. コメント

公開された名前にはコメントを付ける。

コメントは対象となる名前から始め、完全な文章として記述する。

```go
// Package math は基本的な数学関数を提供します。
package math

// Pi は数学定数 π を表します。
const Pi = 3.14159265358979323846

// Sqrt は x の平方根を返します。
// x が負の場合は panic します。
func Sqrt(x float64) float64 {
    if x < 0 {
        panic("math: 負の値の平方根が指定されました")
    }

    // 実装...
    return 0
}
```

```go
// Bad

// 数学関数
package math

// 円周率
const Pi = 3.14159265358979323846

// 平方根を計算
func Sqrt(x float64) float64 {
    // ...
    return 0
}
```

公開された名前のコメントでは、対象となる名前から始める。

### パッケージコメント

パッケージコメントは `package` 宣言の直前に記述する。

```go
// Good

// Package math は基本的な定数と数学関数を提供します.
//
// このパッケージはアーキテクチャ間でビット同一の結果を保証しません.
package math
```

```go
// Bad

package math

// Package math は基本的な定数と数学関数を提供します.
```

パッケージごとにパッケージコメントは1つだけにする。

```go
// Good

// Package math は基本的な定数と数学関数を提供します.
package math
```

```go
// Bad

// Package math は基本的な定数と数学関数を提供します.
package math

// Package math は数学に関する処理を提供します.
```

コメントが長くなる場合は、`doc.go` にパッケージコメントと `package` 宣言だけを配置してもよい。

```go
// doc.go

//
// このパッケージはアーキテクチャ間でビット同一の結果を保証しません.
```

同じ意味を持つ値がコード中に2回以上登場する場合、または値の意味がリテラルだけでは読み取れない場合は、名前付き定数にする。

```go
// Good
const MaxRetryCount = 3

for i := 0; i < MaxRetryCount; i++ {
    // ...
}
```

```go
// Bad

}
```

1回しか使われず、かつ文脈から意味が明確な値（例：`len(s) == 0`の`0`）は、無理に定数化しない。

## 30. 初期化・エラー生成の統一ルール

以下は、複数の書き方が並立しうる細かな書き方について、本規約で統一したものである。当初は「プロジェクト内の既存の書き方に合わせる」という方針を取っていたが、本プロジェクトはRailsからGoへの新規移行であり、判断基準となる既存Goコードが存在しないため機能しなかった。そのため、以下のとおり本規約で決定する。ここに挙げていない同種の細かい書き方について、際限なく新たな独自ルールを追加することは避ける。

### ゼロ値によるローカル変数初期化

ローカル変数は零値（`var x []T`）で初期化することを基本とする。「12. `nil`の扱い」のとおり、nilスライスは`len()`・`range`に対して安全であり、空の複合リテラルより簡潔である。

```go
// Good
var users []User

for _, u := range candidates {
    if u.Active {
        users = append(users, u)
    }
}
```

```go
// Bad
users := []User{} // nilを避ける理由がない場面で複合リテラルを使う
```

ただし、HTTPレスポンスとしてJSON化するResponse DTOのスライスフィールドは、要素が0件の場合に`null`ではなく`[]`を返す必要があるため、空の複合リテラル（`[]T{}`）で明示的に初期化する（「16. 構造体タグ」参照）。

```go
// Good
type ListTasksResponse struct {
    Tasks []TaskResponse `json:"tasks"`
}

func toListResponse(tasks []Task) ListTasksResponse {
    items := make([]TaskResponse, 0, len(tasks)) // 0件でもnullを返さない

    for _, t := range tasks {
        items = append(items, toTaskResponse(t))
    }

    return ListTasksResponse{Tasks: items}
}
```

### `new` と空の複合リテラルの使い分け

`new(T)`ではなく`&T{}`を使用する。フィールドの初期化を同じ式の中で行えるため。

```go
// Good
user := &User{}
```

```go
// Bad
user := new(User)
```

### `make` と空の複合リテラルの使い分け

サイズが事前に分かる場合は「27. パフォーマンス」のとおり`make([]T, 0, n)`で容量を確保する。サイズが不明で、かつnilを許容しない場面（前述のResponse DTO等）では`[]T{}`を使用する。容量指定のない`make([]T, 0)`は使用しない（`[]T{}`と等価で冗長）。

```go
// Good
results := make([]Result, 0, len(items)) // 容量が既知
```

```go
// Good
items := []TaskResponse{} // 容量不明・nil不可
```

```go
// Bad
results := make([]Result, 0) // []Result{} と等価で、容量指定の意味がない
```

### `cmp.Diff` の `got` / `want` の順序

`cmp.Diff(got, want)`の順序に統一する。「26. テスト」の他のテスト例が一貫して`got`を先に置いているため、それに合わせる。

```go
// Good
if diff := cmp.Diff(got, want); diff != "" {
    t.Errorf("結果が一致しません (-got +want):\n%s", diff)
}
```

```go
// Bad
if diff := cmp.Diff(want, got); diff != "" {
    t.Errorf("結果が一致しません (-want +got):\n%s", diff)
}
```

### `errors.New` と `fmt.Errorf` の使い分け

値の埋め込みやエラーのラップが不要な固定メッセージには`errors.New`を、値を埋め込む場合やエラーをラップする場合（「18. エラーハンドリング」の`%w`）には`fmt.Errorf`を使用する。

```go
// Good
var ErrUserNotFound = errors.New("user not found") // 固定メッセージ・sentinel error

func FindUser(id string) (*User, error) {
    // ...
    return nil, fmt.Errorf("ユーザー %q の取得に失敗しました: %w", id, ErrUserNotFound) // 値の埋め込み・ラップ
}
```

```go
// Bad
func FindUser(id string) (*User, error) {
    // ...
    return nil, errors.New(fmt.Sprintf("ユーザー %s の取得に失敗しました", id)) // fmt.Errorfで書ける内容をerrors.New(fmt.Sprintf(...))で書く
}
```
