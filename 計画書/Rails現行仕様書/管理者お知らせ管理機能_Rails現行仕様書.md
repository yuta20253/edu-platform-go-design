# 管理者お知らせ管理機能 Rails現行仕様書

---

# 1. 機能概要

- 機能の目的
  - 管理者が、全利用者に向けたお知らせを作成・更新・削除・配信できるようにすること。あわせて高校ごとのお知らせを参照できるようにすること。
- システム上の役割
  - 作成・更新・削除・配信のすべてを担う。3つのお知らせ機能のうち、**削除と手動配信を持つのは本機能のみ**である。
  - **管理者が作成するお知らせは全利用者に届く。** 配信先は「全員」が自動的に1件だけ設定され、所属校による絞り込みを行わない。管理者が配信先を指定する手段はない。
  - 下書き・予約・即時配信のいずれかの状態で作成できる。予約したお知らせは**予約日時を過ぎると自動的に配信済みへ切り替わる。**
  - 高校ごとのお知らせ一覧は、その高校を配信先に含むお知らせを参照する。教員が自校向けに作成したお知らせの確認に使う。
- 利用者
  - `admin` ロールのユーザー（管理者）

---

# 2. 機能一覧

|操作|概要|
|-|-|
|お知らせ一覧取得|管理者が発行したお知らせを、件名の検索・状態の絞り込み・ページ指定で取得する|
|お知らせ詳細取得|管理者が発行したお知らせ1件を取得する|
|お知らせ作成|件名・本文・配信方法を指定してお知らせを作成する。配信先は全員で固定|
|お知らせ更新|お知らせの内容・配信方法を部分的に更新する|
|お知らせ削除|配信済みでないお知らせを削除する|
|お知らせ配信|お知らせを手動で配信済みにする|
|高校別お知らせ一覧取得|指定した高校を配信先に含むお知らせを取得する|

# 3. 業務フロー

## お知らせの作成と配信

1. 管理者が件名・本文・配信方法（下書き・予約・即時配信）を入力する。
2. システムは入力内容を検証する。
3. システムはお知らせを作成し、配信先として「全員」を1件設定する。
4. 下書きで作成した場合、管理者は後から内容を更新したうえで配信する。
5. 予約で作成した場合、予約日時を過ぎると自動的に配信済みへ切り替わる。
6. 手動で配信する場合、システムは状態を配信済みにし、予約日時を消す。

## お知らせの削除

1. 管理者が削除を要求する。
2. システムは操作者に権限があることを確認する。
3. システムはお知らせが配信済みでないことを確認する。配信済みの場合はエラーとして返す。
4. システムはお知らせと配信先を削除する。

## 高校別お知らせの確認

1. 管理者が高校を選び、その高校のお知らせ一覧を要求する。
2. システムは指定された高校を配信先に含むお知らせを取得する。
3. その高校に向けられた配信先だけを抜き出して返す。

# 5. API / 処理詳細

## `Api::V1::Admin::AnnouncementsController#index`

### 概要

管理者が発行したお知らせを、件名の検索・状態の絞り込み・ページ指定で返す。

### Request

|項目|必須|型|説明|
|-|-|-|-|
|`q`|任意|string|件名の一部。部分一致で絞り込む|
|`status`|任意|string|`draft` / `scheduled` / `published`。既知でない値は未指定として扱う|
|`page`|任意|integer|ページ番号。0以下・数値以外は未指定として扱う|
|`per_page`|任意|integer|1ページあたりの件数。既定20、上限100|

### 処理内容

1. 管理者が発行したお知らせを対象とする。
2. `q` が指定されていれば件名の部分一致で絞り込む。
3. `status` が既知の値であれば状態で絞り込む。
4. 作成日時の降順、同値なら識別子の降順に並べる。
5. 指定されたページを取得し、発行者と配信先をあわせて返す。

### 業務ルール

- **対象は管理者が発行したお知らせのみ。** 教員が発行したお知らせは一覧に現れない。発行者のロールが管理者であることで絞り込む。
- 発行者が論理削除済みの管理者であっても対象に含まれる。
- `q` は件名に対する部分一致。本文は検索しない。**検索語に含まれるワイルドカード文字はエスケープされる。**
- `status` が既知の値（`draft` / `scheduled` / `published`）でない場合は絞り込みを行わない。エラーにしない。
- 並び順は**作成日時の降順**。他のお知らせ一覧（配信日時の降順）と異なる。下書き・予約を含むため、配信日時では並べられない。
- 該当するお知らせがない場合は空の配列とページ情報を返す。

### Database変更

- なし

### Response

HTTP Status は `200`。

|項目|型|説明|
|-|-|-|
|`announcements[].id`|integer|お知らせの識別子|
|`announcements[].title`|string|件名|
|`announcements[].status`|string|状態|
|`announcements[].target_type`|string / null|**最初の配信先の種類。** 配信先が0件のときは `null`|
|`announcements[].published_at`|datetime / null|配信日時|
|`announcements[].scheduled_at`|datetime / null|予約日時|
|`announcements[].created_at`|datetime|作成日時|
|`announcements[].publisher`|object|発行者（`id` / `name` / `name_kana`）|
|`meta`|object|`current_page` / `total_pages` / `total_count` / `per_page`|

**本文（`content`）を返さない。** 一覧では件名までとする。生徒向け・教員向けの一覧が本文を返すのとは異なる。

`target_type` は配信先の1件目のみを返す。管理者が作成したお知らせは配信先が「全員」1件であるため常に `all_users` となるが、教員が作成したお知らせが混ざることはないため実害はない。

### Errorケース

|条件|HTTP Status|内容|
|-|-|-|
|該当なし|200|空の配列とページ情報を返す|
|未認証|401|認証されていない|
|`admin` ロール以外|403|`{"errors": ["この操作を行う権限がありません"]}`|

## `Api::V1::Admin::AnnouncementsController#create`

### 概要

件名・本文・配信方法を指定してお知らせを作成する。配信先は「全員」で固定される。

### Request

|項目|必須|型|説明|
|-|-|-|-|
|`announcement[title]`|必須|string|件名。255文字以内|
|`announcement[content]`|必須|string|本文。10,000文字以内|
|`announcement[status]`|必須|string|`draft` / `scheduled` / `published`|
|`announcement[scheduled_at]`|条件付き必須|datetime|予約日時。`status` が `scheduled` のときに必須|

**配信先を指定する項目はない。**

### 処理内容

1. 件名・本文・状態の必須と、状態の値を検証する。
2. 検証に失敗した場合はエラーを返す。
3. お知らせを作成する。
4. 配信先として「全員」を1件作成する。所属校による絞り込みを行わない。
5. 成功のメッセージを返す。

お知らせの作成と配信先の作成は1つのトランザクションで行う。

### 業務ルール

- **配信先は「全員」の1件に固定される。** 高校・学年・権限・ユーザーによる絞り込みはできない。管理者が作成したお知らせは全利用者に届く。
- 教員が作成する場合に行われる「発行者の所属校を付与して自校内に絞り込む」処理を行わない。管理者は所属校を持たないため、付与しても意味がない。
- 発行者は操作者である。
- システムが自動生成したお知らせではないため、`system_generated` は `false` となる。

#### 入力の検証

|項目|ルール|エラーメッセージ|
|-|-|-|
|件名|必須（Form）、255文字以内（モデル）|`Title を入力してください` / `Title は255文字以内で入力してください`|
|本文|必須（Form）、10,000文字以内（モデル）|`Content を入力してください` / `Content は10000文字以内で入力してください`|
|状態|必須（Form）、`draft` / `scheduled` / `published` のいずれか|`Status を入力してください` / `Status は一覧にありません`|
|予約日時|状態が `scheduled` のとき必須、かつ未来日時（モデル）|`配信日時 を指定してください` / `配信日時 は未来日時を指定してください`|

件名・本文・状態の項目名が英語表記になるのは、日本語訳が定義されていないためである。予約日時のみ「配信日時」という訳がある。

本文の長さはモデルでは10,000文字以内だが、**DBの列は65,535文字まで保持できる。** 検証の方が厳しい。

### Database変更

作成:

```
announcements
announcement_targets
```

### Response

HTTP Status は `201`。

|項目|型|説明|
|-|-|-|
|`message`|string|お知らせを作成しました。|

**作成したお知らせの識別子を返さない。** 教師お知らせ機能の作成が `announcement_id` を返すのとは異なる。

### Errorケース

|条件|HTTP Status|内容|
|-|-|-|
|入力の検証に失敗|422|`{"errors": [メッセージ, ...]}`。複数同時に含まれうる|
|`announcement` パラメータ自体が存在しない|400|必須パラメータ不足として扱われ、個別のエラー本文は定義されていない|
|未認証|401|認証されていない|
|`admin` ロール以外|403|`{"errors": ["この操作を行う権限がありません"]}`|

## `Api::V1::Admin::AnnouncementsController#update`

### 概要

お知らせの内容・配信方法を部分的に更新する。

### Request

|項目|必須|型|説明|
|-|-|-|-|
|`id`|必須|integer|お知らせの識別子。パスに含まれる|
|`announcement[title]`|任意|string|件名|
|`announcement[content]`|任意|string|本文|
|`announcement[status]`|任意|string|状態|
|`announcement[scheduled_at]`|任意|datetime|予約日時|

### 処理内容

1. 管理者が発行したお知らせの範囲で、指定された識別子のものを取得する。該当しない場合はエラーを返す。
2. 操作者に権限があることを確認する。ない場合はエラーを返す。
3. 状態の値を検証する。
4. **渡された項目のみ**を更新する。
5. 成功のメッセージを返す。

### 業務ルール

- **部分更新である。** リクエストに含まれなかった項目は更新しない。件名を渡さずに本文だけを更新できる。
- 更新時は件名・本文・状態の**必須検証を行わない。** 作成時のみ必須である。ただし件名・本文を空文字で渡した場合は、モデル側の必須検証で拒否される。
- 状態の値の検証（既知の3つのいずれか）は更新時も行う。
- 状態の遷移は許される組み合わせに限る。下書き → 予約・配信済み、予約 → 配信済みのみ。それ以外は `status は {遷移元} から {遷移先} へは変更できません` を返す。
- **配信済みのお知らせは編集できない。** `is 配信済みのため編集できません` を返す。
- 配信先を更新する手段はない。作成時の「全員」が維持される。
- 権限の確認は「操作者が発行者であること」または「発行者が論理削除済みであること」を求める（「8. 権限制御」）。

### Database変更

更新:

```
announcements
```

### Response

HTTP Status は `200`。

|項目|型|説明|
|-|-|-|
|`message`|string|お知らせを更新しました。|

### Errorケース

|条件|HTTP Status|内容|
|-|-|-|
|状態の値が既知でない|422|`{"errors": ["Status は一覧にありません"]}`|
|状態の遷移が許されない組み合わせ|422|`{"errors": ["status は {遷移元} から {遷移先} へは変更できません"]}`|
|配信済みのため編集できない|422|`{"errors": ["is 配信済みのため編集できません"]}`|
|件名・本文がモデルの検証に失敗|422|`{"errors": [メッセージ, ...]}`|
|操作者に権限がない|403|`{"errors": ["この操作を行う権限がありません"]}`|
|教員が発行した、存在しない|404|`{"message": "Announcementが見つかりません"}`|
|`announcement` パラメータ自体が存在しない|400|必須パラメータ不足として扱われる|
|未認証|401|認証されていない|
|`admin` ロール以外|403|同上|

配信済みの編集を拒否するメッセージが `is 配信済みのため編集できません` となるのは、検証の対象が特定の項目ではなく全体であるためである。項目名の位置に `is` が入る。

## `Api::V1::Admin::HighSchools::AnnouncementsController#index`

### 概要

指定した高校を配信先に含むお知らせを返す。

### Request

|項目|必須|型|説明|
|-|-|-|-|
|`high_school_id`|必須|integer|高校の識別子。パスに含まれる|
|`page`|任意|integer|ページ番号|
|`per_page`|任意|integer|1ページあたりの件数。既定20、上限100|

### 処理内容

1. 指定された高校を取得する。存在しない場合はエラーを返す。
2. その高校を配信先に含むお知らせを取得する。
3. 作成日時の降順、同値なら識別子の降順に並べる。
4. 指定されたページを取得する。
5. お知らせごとに、**その高校に向けられた配信先だけを抜き出して**返す。

### 業務ルール

- **高校の実在確認を行う。** 存在しない識別子は `404` となる。
- 対象は「配信先の高校がその高校であるお知らせ」である。発行者のロールを問わない。**教員が自校向けに作成したお知らせが主な対象になる。**
- 管理者が作成したお知らせは配信先が「全員」で高校が未設定であるため、この一覧には現れない。
- 状態による絞り込みを行わない。下書き・予約も含まれる。
- 件名の検索・状態の絞り込みの手段はない。
- 複数の配信先が同じ高校を指すお知らせも1件として返る（重複しない）。
- **レスポンスに含める配信先は、その高校に向けられたものだけである。** 他校・全校向けの配信先は除かれる。

### Database変更

- なし

### Response

HTTP Status は `200`。

|項目|型|説明|
|-|-|-|
|`announcements[].id`|integer|お知らせの識別子|
|`announcements[].title`|string|件名|
|`announcements[].content`|string|本文|
|`announcements[].status`|string|状態|
|`announcements[].published_at`|datetime / null|配信日時|
|`announcements[].scheduled_at`|datetime / null|予約日時|
|`announcements[].created_at`|datetime|作成日時|
|`announcements[].targets`|array|その高校に向けられた配信先|
|`announcements[].targets[].id`|integer|配信先の識別子|
|`announcements[].targets[].target_type`|string|配信先の種類|
|`announcements[].targets[].high_school_id`|integer / null|高校の識別子|
|`announcements[].targets[].grade_id`|integer / null|学年の識別子|
|`announcements[].targets[].user_role_id`|integer / null|権限の識別子|

**本文を返す。** 管理者向けのお知らせ一覧が本文を返さないのとは異なる。配信先の項目名が `targets` であり、教師お知らせ機能の編集フォームの `announcement_targets` とも異なる。

# 6. データモデル

本機能が参照・更新するテーブルは、お知らせ機能①「6. データモデル」が整理している `announcements`・`announcement_targets` と同じである。加えて一覧の絞り込み・高校別一覧で `users`・`user_roles`・`high_schools` を参照する。

|テーブル|役割|本機能での使い方|
|-|-|-|
|`announcements`|お知らせ本体|作成・更新・削除・配信・参照|
|`announcement_targets`|お知らせの配信先|作成（全員1件）・削除・参照|
|`users`|ユーザー|発行者、発行者のロールによる絞り込み、発行者の論理削除状態による権限判定|
|`user_roles`|ロール|管理者が発行したお知らせの絞り込み|
|`high_schools`|高校|高校別一覧の実在確認|

リレーション・列の意味・状態と配信先の種類の対応は、お知らせ機能①「6. データモデル」のとおりである。

本機能に固有の点:

- **管理者が作成したお知らせの配信先は常に「全員」1件で、高校が未設定である。** そのため全利用者にマッチし、高校別一覧には現れない。
- 一覧・詳細・更新・削除・配信の対象を「発行者のロールが管理者であるお知らせ」で絞り込む。発行者が論理削除済みの管理者であっても対象に含まれる。
- `announcements` に論理削除の列がないため、削除は物理削除である。

# 7. 状態管理

状態と遷移の規則は、お知らせ機能①「7. 状態管理」のとおりである。本機能が関与するのは次の経路である。

|操作|状態の変化|
|-|-|
|作成（`draft`）|なし（下書きで作成）|
|作成（`scheduled`）|なし（予約で作成）。予約日時が必須かつ未来日時|
|作成（`published`）|なし（配信済みで作成）。配信日時に現在時刻が設定される|
|更新|下書き → 予約・配信済み、予約 → 配信済みのみ許される|
|配信（手動）|下書き・予約 → 配信済み。**予約日時を消す**|
|配信（自動切替）|予約 → 配信済み。**予約日時を消さない**（「9. 非同期処理」）|
|削除|配信済みでない場合のみ可能|

```
draft（下書き）
  ├─→ scheduled（予約）        更新
  └─→ published（配信済み）     更新 / 手動配信

scheduled（予約）
  └─→ published（配信済み）     更新 / 手動配信 / 自動切替

published（配信済み）
  └─→ （遷移先なし。編集・削除も不可）
```

- 配信済みのお知らせは編集・削除・再配信のいずれもできない。
- **手動配信と自動切替で予約日時の扱いが異なる。** 手動配信は予約日時を `null` にし、自動切替はそのまま残す。配信済みのお知らせに予約日時が残っているかどうかで、どちらの経路で配信されたかが分かる状態になっている。

# 8. 権限制御

- 利用可能ユーザー: `admin` ロールのユーザーのみ。
- 未認証のアクセスは `401`。`admin` 以外のロールは `403`。

|操作|権限の確認|
|-|-|
|一覧・詳細|**行わない。** 管理者が発行したお知らせであれば、他の管理者のものも参照できる|
|作成|行わない。発行者は操作者になる|
|更新・削除・配信|**行う。** 操作者が発行者であること、または発行者が論理削除済みであること|
|高校別一覧|行わない|

更新・削除・配信の条件を詳しく示す。

- 操作者が `admin` ロールであること（前提）
- かつ、次のいずれかを満たすこと
  - お知らせの発行者が操作者自身である
  - **お知らせの発行者が論理削除済みである**

**発行者が論理削除済みの場合に他の管理者へ操作を許すのは、退職した管理者のお知らせが編集も削除もできなくなることを防ぐためである。**

- 対象の絞り込み（発行者のロールが管理者）と権限の確認（発行者が操作者か）は別の段階である。教員が発行したお知らせは絞り込みで除かれて `404` となり、他の管理者が発行したお知らせは絞り込みを通過してから権限の確認で `403` となる。
- 高校別一覧は、全高校のお知らせを参照できる。操作者の所属校による制限はない（管理者は所属校を持たない）。

# 9. 非同期処理

## 予約配信の自動切替

予約状態のお知らせを、予約日時を過ぎたときに配信済みへ切り替える処理が存在する。

|項目|内容|
|-|-|
|実行タイミング|**毎分**。定期実行の設定（`config/schedule.yml`）に `*/1 * * * *` として登録されている|
|有効・無効|**環境変数 `ENABLE_SIDEKIQ_CRON` が `true` のときのみ有効。** かつワーカープロセスとして起動している場合に限る。本番で有効かどうかはコードから判断できない|
|対象|状態が予約で、予約日時が現在時刻以前のお知らせ。発行者のロールを問わないため、**管理者が作成したものも教員が作成したものも対象になる**|
|処理内容|対象を1件ずつ取り出し、排他ロックを取ってから状態を配信済みに更新する|
|予約日時の扱い|**消さない。** 手動配信が予約日時を `null` にするのとは異なる|
|配信日時|状態が配信済みに変わるため、配信日時に現在時刻が設定される|
|失敗時の扱い|**1件が失敗しても、ほかの件の処理を続ける。** 失敗した件は記録に残し、次回の実行で再び対象になる|
|記録|成功した件は識別子を記録する。失敗した件は識別子と例外の種類・内容を記録する|

- 対象の取得はまとめて行うが、更新は1件ずつ行う。1件ごとに排他ロックを取るため、同じお知らせが二重に配信されることはない。
- 予約日時が過去のまま下書きに戻されることはない。状態の遷移が予約 → 配信済みの一方向であるためである。
- この処理によって、生徒向け・教員向けのお知らせ一覧に新たなお知らせが現れる（お知らせ機能①「9. 非同期処理」）。

## その他

- 作成・更新・削除・配信はすべてリクエスト時に同期で実行される。
- メール送信・通知の送信は行わない。お知らせは利用者が一覧を開いたときに読まれる。
