## 決定した10点と、反映する内容

### 1. 権限更新の入口: 1か所にまとめる

- **決定**: 教員の権限(`grade_scope` / `manage_other_teachers`)の書き換えを、`teacher-permission`に一本化する。管理者の教員更新も、それを呼ぶ。保護ルール(自己更新不可・最後の教員は更新不可)は、「操作者が教師のとき」だけ適用する(Railsと同じ挙動)
- **背景**: Railsでは、教師の画面にだけ保護ルールがあり、管理者の画面は同じ項目を保護ルールなしで更新している
- **反映先**:
  - `GO移行・設計仕様書/教師権限管理機能_Go移行・設計仕様書.md`、`Go実装仕様書/教師権限管理機能_Go実装仕様書.md`: 操作者の種別(教師/管理者)を入力に加え、管理者経路から呼べるようにする
  - `GO移行・設計仕様書/管理者教員管理機能_Go移行・設計仕様書.md`、`Go実装仕様書/管理者教員管理機能_Go実装仕様書.md`: `UpdateTeacher`が権限を自分で書き換える記述をやめ、`teacher-permission`の操作を呼ぶ形にする。`TeacherPermissionStore.Update`の呼び出しを外す
  - Context間の依存の向き(`teacher-management`→`teacher-permission`)が、既存の依存(`teacher-permission`→`teacher-management`)と循環しないか確認する。循環する場合は、規約5章に従って責務を見直す

### 2. ディレクトリ名: Context名から`-`を取り除いた連結形にする(省略しない)

- **当初の決定(2026-09-24)**: Context名のハイフンをアンダースコアにしたもの(snake_case)。省略しない
- **決定の変更(2026-10-29、規約4章に反映済み)**: `-`を取り除いて連結した全小文字の名前にする。省略しない
  - `task-management` → `internal/taskmanagement/`
  - `teacher-management` → `internal/teachermanagement/`
- **変更の理由**: package名にはアンダースコアを使わないため(コーディング規約3章)、ディレクトリ名だけをsnake_caseにすると`internal/task_management/`に`package taskmanagement`を置くことになり、ディレクトリ名とpackage名が一致しない。一致しないと、importのたびに明示的な別名が必要になる(`goimports`が別名を書き込む)。Goの標準ライブラリも複合語を連結する(`tabwriter`・`httputil`・`filepath`)
- **あわせて決まった内部構成**(規約4章):
  - Contextディレクトリ直下: `context.go`(`NewContext`)・`dependency.go`(他Contextへの依存を宣言するインターフェース)
  - `infrastructure/gormrepo/`: Repository実装・GORMモデル

### 優先度の目安

- **A1・A7 は影響が分かりやすく、修正の副作用も小さい**。A1 はメッセージが1件になるだけ、A7 は並び順が決定的になるだけである
- **A9 は提出の判定結果が変わる**。従来 `completed` にならなかったタスクが `completed` になりうるため、フロントエンドの確認が必要。バッチ4のコース参照②で判明し、同②では Rails 現行のまま除外しない形にしている(2026-11-07)
- **A3・A4・A5 は500を422に変える**。フロントが入力エラーとして扱える形になるため、利用者に伝わる情報が改善する。ただしステータスコードが変わるためフロントの確認が必要
- **B1・B2 は訳を足すだけで直る**が、フロントがメッセージ文字列を表示している場合は表示が変わる
- **B3・B4・B5 は全機能のエラーハンドリングに波及する**。移行と同時に直すか、移行前に直すかで②③の記述が変わる
- **B5 は Rails 側を直す方針で決定した(2026-11-07)**。確認表示の独自ハンドラを外し、404の本文の形を機能内で統一する。直すまでは問題解答機能③が「`AppError` に本文の形を持たせ、ミドルウェアがそれに従う」仕組みを前提にしている。Rails 側を直したあとは、他機能③と同じ「404なら `message` キー」の分岐に揃えられる
- **A2 は現状到達しない経路**であり、急いで直す必要はない。ただし構造としては残っている
- **A8 は使えない経路が通る**という問題であり、`only:` を付けるだけで直る
- **A10・A11・A12 は分析の数値そのものが変わる**。学年平均・正答率・順位の値が現状より上下するため、変更前に業務側の確認が必要。移行設計では Rails 現行のまま踏襲している(2026-11-07)
- **A13 は500を回避するだけで直る**。学年未設定の生徒に対して何を返すか(0扱い / 422 / 専用のメッセージ)は業務判断が必要
- **A14・A15・A16・A17・A18 はいずれも「保証されていない挙動」**。A15・A16・A17 は Go 側で安定した順序・突き合わせに定めており(分析②「19. API仕様」)、Rails を直せば両者が一致する。A14・A18 は Rails 現行の挙動を踏襲しているため、直す場合は Go 側も合わせる必要がある
- **B6 は訳を足すだけで直る**。ただしフロントエンドが `errors` の文字列をそのまま表示しているため、表示が変わる
- **A21・A22・A27・A28・B8 は同じデータに対する扱いが機能間で揃っていないもの**。どちらに揃えるかの判断が必要で、揃えると一方のレスポンスが変わる。A22 は Go 側が公開操作で年次昇順に定めており、Rails を直せば一致する
- **A23 は住所検索の結果の件数が変わる**。論理削除済みの住所を参照しているユーザーが存在する場合、除外するとプロフィール更新で住所IDが引けなくなる可能性があるため、データの確認が先に必要
- **A25 は使えない経路が通る**という問題であり、`only:` を付けるだけで直る。A8 と同時に対応できる
- **A26 はエスケープを足すだけで直る**。Go側ではエスケープする方針としたため、直せば両者が一致する
- **A20 はページネーションの追加が必要**で、フロントエンドの変更を伴う
- **A29・A32・A33・B11 はいずれも機能間で扱いが揃っていないもの**。どちらに揃えるかの判断が必要で、揃えるとレスポンスまたはデータが変わる。A32 は既定の件数が変わるため、フロントエンドの確認が必要
- **A30 はログの読みやすさの問題**であり、配信の結果そのものは正しい。Go側では更新条件に遷移前の状態を含める形にしており、競合を正常として扱う(規約13章)。Rails を直す場合は `with_lock` の中で `scheduled?` を再確認し、偽なら何もせず戻る形にすればよい
- **A31 は並び順を揃えるかの判断**。管理者側が下書き・予約を含む以上 `published_at` では並べられないため、第2キー(`id` 降順)を揃えるだけでも決定性は改善する
- **B9・B10 は訳と検証の対象の見直しで直る**。B9 は `:base` への検証を項目単位に変えるか、`errors.messages.base` の訳を空にする必要があり、B10 より手間がかかる
- **A34・A39・B13 は機能間で扱いが揃っていないもの**。どちらに揃えるかの判断が必要で、揃えるとレスポンスまたは一覧の件数が変わる
- **A36・A37 は管理者が招待した教員のデータ品質の問題**。A36 は `password_reset_required: true` を設定するだけで直るが、既存データの扱い（すでに作成済みの教員を招待待ちに戻すか）を決める必要がある。A37 は画面に氏名カナの入力欄を足す必要があり、フロントの変更を伴う
- **A38 は500を回避するだけで直る**。権限レコードがない教員に対して何を返すか（作成する / 422 / 無視する）は業務判断が必要
- **A35・A40 はページネーションの追加が必要**で、フロントエンドの変更を伴う。A20と同時に対応できる
- **B12 は意図した使い分け**であり、不具合ではない。フロント側の型定義を2つに分けるか、常に `lock_version` を返すかの判断である
